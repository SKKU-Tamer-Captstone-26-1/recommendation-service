# Flutter Recommendation Handoff

## Purpose

This document records the Flutter-facing recommendation contract after the Plan
012 Cloud Run deployment.

Production mobile traffic must go through `app-gateway-service`. Flutter must
not call private `recommendation-service` directly in production.

## Production Endpoint Direction

Production mobile flow:

```text
Flutter
  -> app-gateway-service
      -> recommendation-service
```

`recommendation-service` remains private at the Cloud Run IAM layer.
`app-gateway-service` is responsible for sending Cloud Run server-to-server
authentication and forwarding the user's auth-service bearer token.

The gateway handoff is documented in:

```text
docs/api/app-gateway-handoff.md
```

## Direct Service Endpoint

Direct recommendation-service gRPC host for internal smoke tests and gateway
downstream configuration:

```text
recommendation-service-vcuepibcwq-du.a.run.app:443
```

Public Cloud Run URL:

```text
https://recommendation-service-vcuepibcwq-du.a.run.app
```

Protocol:

```text
gRPC over TLS
```

This endpoint is not a Flutter production target while Cloud Run IAM is private.

## Auth Metadata

Every recommendation RPC except standard gRPC health must include the JWT issued
by `auth-service`:

```text
authorization: Bearer <auth-service-jwt>
```

Flutter must not send `user_id` or `external_user_id` in recommendation
requests. `recommendation-service` resolves the user from JWT `sub`.
In deployed staging, recommendation-service resolves the bearer token by
calling auth-service gRPC `ValidateToken`; it does not issue or decode tokens as
an auth owner.

When the service is private, `app-gateway-service` must also send Cloud Run IAM
metadata:

```text
x-serverless-authorization: Bearer <google-id-token-for-recommendation-service>
```

The gateway must preserve the user token in `authorization` and must not replace
it with the Google ID token.

Current deployed smoke evidence:

```text
grpc_health = SERVING
Cloud Run without invoker auth = 401/403 before service code
GetProfileStatus with x-serverless-authorization + auth JWT = PROFILE_STATUS_ACTIVE
```

## Beverage Image Metadata

Beverage recommendation cards may display:

```text
recommendation.metadata["image_url"]
recommendation.metadata["image_alt_text_ko"]
recommendation.metadata["image"]
```

`image_url` is app display metadata owned by recommendation-service catalog
state. In MVP it can be either a source-checked direct product/cocktail
representative image or a category fallback image.

Flutter expectations:

- Show `metadata.image_url` when it is a non-empty URL.
- Treat `metadata.image_url` as the display URL. In staging/production this may
  be an ONTHEBLOCK-managed cache/CDN URL, not the original source URL.
- Use `metadata.image.original_image_url` and `metadata.image.source_url` only
  for traceability, debugging, attribution, or credits surfaces.
- Use a local placeholder if the network image fails.
- Do not rerank, filter, or infer recommendation quality from the image.
- Preserve `metadata.image.license`, `metadata.image.attribution`, and
  `metadata.image.attribution_required` for a detail or credits surface.
- Treat `metadata.image.image_kind = category_representative` as a representative
  category fallback image.
- Treat `metadata.image.image_kind = licensed_product_representative` or
  `licensed_cocktail_representative` as a source-checked display image, not as
  live inventory, venue availability, or recommendation quality evidence.

## Beverage Budget Trade-off Metadata

Beverage recommendation cards may display:

```text
recommendation.metadata["source"]["budget_tradeoff"]["display_label_ko"]
recommendation.metadata["source"]["budget_tradeoff"]["note_ko"]
```

`budget_tradeoff` is generated by recommendation-service from soft catalog price
observations. It is not a live store price, menu price, inventory status, or
strict affordability guarantee.

Flutter expectations:

- Show `display_label_ko` or `note_ko` only as explanatory helper text.
- Do not filter or rerank cards from `budget_tradeoff.status`.
- Treat `source = catalog_price_not_live_offer` as non-live catalog evidence.
- Prefer map-service/place-service price metadata later when displaying live
  venue/store offer details.

## Recommended Call Order

1. Flutter calls app-gateway.
2. App-gateway validates or forwards user auth metadata according to its auth
   contract.
3. App-gateway calls `recommendation-service` with:
   - `authorization: Bearer <auth-service-jwt>`
   - `x-serverless-authorization: Bearer <google-id-token>`
4. Recommendation-service resolves user identity through auth-service.
5. Gateway returns the response to Flutter without reranking or rewriting
   recommendation decisions.

If `GetProfileStatus` is not active, Flutter should show the survey/profile
pending state instead of requesting recommendations.

## Beverage Request

Minimal staging request:

```text
GetBeverageRecommendations(
  category: "",
  limit: 10,
  budget_mode: BUDGET_MODE_SOFT
)
```

Strict budget mode is intentionally unavailable until approved canonical
price/map snapshot semantics are deployed.

For follow-up recommendation UX, Flutter should keep displaying the server
order and may send the previous result context through the gateway:

```text
exclude_beverage_ids: ["<previous_beverage_uuid>"]
exclude_result_ids: ["<previous_recommendation_result_uuid>"]
diversity_mode: BEVERAGE_DIVERSITY_MODE_DIFFERENT
```

For taste-direction follow-up UX, Flutter/chatbot should pass the user's
direction as a server-owned recommendation control instead of filtering on the
client:

```text
flavor_direction: BEVERAGE_FLAVOR_DIRECTION_SWEETER
flavor_direction: BEVERAGE_FLAVOR_DIRECTION_LESS_SWEET
flavor_direction: BEVERAGE_FLAVOR_DIRECTION_SMOKIER
flavor_direction: BEVERAGE_FLAVOR_DIRECTION_LESS_SMOKY
flavor_direction: BEVERAGE_FLAVOR_DIRECTION_LIGHTER
flavor_direction: BEVERAGE_FLAVOR_DIRECTION_RICHER
flavor_direction: BEVERAGE_FLAVOR_DIRECTION_MORE_HERBAL_BITTER
flavor_direction: BEVERAGE_FLAVOR_DIRECTION_BRIGHTER_FRUITY
```

Flutter should not infer these directions from local card data. The expected
production flow is:

```text
Flutter -> app-gateway-service -> chatbot-service -> recommendation-service
```

If Flutter has a non-chatbot surface that explicitly exposes a direction button,
it may send the selected enum through the gateway contract, but the response
order still belongs to recommendation-service.

Flutter must not score, rerank, or invent substitute beverages. If the service
returns fewer results after exclusions, the UI should show the smaller response
or ask the user for a narrower preference.

## Venue Place Type Filter

When a selected beverage and user location are available, Flutter or
app-gateway-service may pass venue intent as `place_types` to
`GetVenueRecommendations`.

Examples:

```text
place_types: ["store"]
place_types: ["bar"]
place_types: ["outdoor"]
```

These values are recommendation request filters, not canonical place writes.
`recommendation-service` resolves friendly values to known map/place snapshot
types, ranks the filtered candidates, and returns the original snapshot
`place_type` in each result.

Flutter must:

- preserve the response order exactly as returned
- not convert `store` into local SQL or client-side filtering
- not invent venue candidates if the response is empty
- show an insufficient-data or location-needed state when required context is
  missing

## User Location Source

Venue ranking needs WGS84 user coordinates:

```text
GetVenueRecommendations.lat
GetVenueRecommendations.lng
```

`auth-service` currently owns user identity and profile fields such as
`neighborhood`. That neighborhood value is useful for onboarding/display, but it
is not precise enough for venue distance scoring. Flutter or app-gateway-service
must forward the latest approved user coordinates when requesting venue
recommendations.

Allowed production paths:

```text
Flutter location permission / map picker
  -> app-gateway-service
  -> GetVenueRecommendations(lat, lng, ...)

auth/gateway approved user-location metadata with WGS84 coordinates
  -> app-gateway-service
  -> GetVenueRecommendations(lat, lng, ...)
```

Do not send Kakao API keys or raw Kakao response payloads to
`recommendation-service`. Kakao remains a Flutter/map-service lookup or display
concern unless a reviewed storage policy explicitly changes that boundary.

## Venue Distance Display

Venue recommendations may return straight-line or route-aware distance metadata.
Flutter must treat `distance_strategy=straight_line_mvp` as an approximate
straight-line distance, not real walking, driving, or transit distance.

Display route-style labels only when response metadata says:

```text
is_route_distance: true
route_distance_m: <present>
```

If `distance_fallback_used=true`, route lookup was attempted but the
recommendation result fell back to straight-line distance. In that case, use
neutral copy such as approximate nearby distance and keep recommendation order
exactly as returned by the service.

## Feedback Events

Allowed `metadata` keys for `RecordRecommendationEvent`:


Use a stable idempotency key per client event:

```text
<session_id_hash>:<result_id>:<event_type>
```

## Current Caveats

- Deployed survey-service does not yet expose cursor-based
  `ListSurveyEvents` / `GetSurveyResponse`.
- A safe deployed survey user or survey ID is still needed to generate a real
  active staging profile with `app.tools.survey_result_adapter`.
- Venue recommendations require map/place snapshot data. Beverage
  recommendations are the first Flutter target.
