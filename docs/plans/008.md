# Drink Recommendation Precision and AI Model Readiness

## 1. Goal

Make drink-only recommendations more precise and prepare the system for a future
learned ranking model without depending on map-service or survey-service being
deployed.

The slice must:

- keep deterministic scoring as the production ranking path
- add an offline recommendation evaluation harness
- define golden user/profile fixtures and expected drink outcomes
- measure recommendation quality before changing weights
- improve drink ranking precision with versioned scoring changes only
- log model-ready features for later training
- make clear that a learned model is not production-ready until real feedback
  data exists

## 2. Non-Goals

- Do not deploy a neural or LLM ranking model to production in this slice.
- Do not use an LLM as the recommendation score source.
- Do not implement map-service or survey-service.
- Do not require live venue distance, inventory, or price data.
- Do not change public protobuf fields.
- Do not mutate raw survey answers or read survey-service databases.
- Do not add Kafka, Redis, Airflow, feature stores, or separate ML serving.
- Do not make Qdrant the final ranking engine.

## 4. Ownership Analysis

| Data | Owner | This task writes? | This task reads? | Allowed? |
|---|---|---:|---:|---|
| Derived profile fixtures | recommendation-service test/eval data | yes | yes | yes |
| Beverage catalog/vectors | recommendation-service | no | yes | yes |
| Scoring configs | recommendation-service | yes | yes | yes |
| Recommendation logs | recommendation-service | yes | yes | yes |
| Evaluation reports | recommendation-service artifacts | yes | yes | yes |
| Raw survey answers | survey-service | no | no | yes |
| Canonical venue/menu/inventory/price | map-service/place-service | no | no | yes |
| User identity | auth-service | no | auth context only | yes |

Boundary decision:

```text
deterministic drink ranking + offline evaluation + model-ready feature logging.
```

Harness boundary answers:

1. Recommendation-owned scoring and evaluation artifacts are affected.
2. recommendation-service may write scoring configs, logs, and local evaluation
   artifacts.
3. This service must not directly read survey-service or map-service databases.
4. This is deterministic recommendation logic and offline evaluation.
5. Admin Page is not involved.
6. No Kakao response data is stored.
7. Recommendation reproducibility is directly affected, so scoring changes must
   be versioned and evaluation reports must be reproducible.
8. RAG boundaries are unaffected.

## 5. Proposed Change

Add a drink recommendation evaluation and precision layer on top of the improved
catalog from plan 007.

Implementation readiness gate:

```text
service boundary | recommendation contract | database contract |
verification contract
```

The smallest useful implementation:

- Add offline evaluation fixtures:

```text
data/evaluation/drink_profiles_v1.json
```

- Each fixture defines:
  - profile name
  - synthetic survey/profile input
  - expected categories/styles
  - positive drink IDs or catalog keys
  - negative drink IDs or catalog keys
  - explanation expectations
- Add an evaluation service and CLI:

```text
python -m app.tools.evaluate_drink_recommendations
```

- Report metrics:
  - top-k hit rate against expected positives
  - category/style match rate
  - negative-result violation count
  - average similarity/final score for positives vs negatives
  - explanation reason-code coverage
  - profile/category coverage
- Add model-ready feature logging to recommendation result debug metadata:
  - taste similarity
  - category fit
  - budget fit
  - experience fit
  - popularity/quality proxy
  - diversity adjustment
  - matched dimensions
  - scoring config version
  - vector schema version
- Tune deterministic scoring only through a new versioned scoring config if
  evaluation proves a change is better than the baseline.

Scoring version rule:

```text
Do not silently alter scoring_v1. Add scoring_v2 only if weights or reason-code
rules change, then update active_scoring_config intentionally.
```

Future learned model readiness:

```text
The first "real AI model" should be trained only after enough explicit or
implicit user feedback exists. This plan prepares feature logs and evaluation
fixtures, but production ranking remains deterministic.
```

## 6. Database Plan

No schema migration is expected for the first implementation.

Existing tables used:

- `scoring_configs`
- `recommendation_requests`
- `recommendation_results`
- `recommendation_explanations`
- `recommendation_interactions`
- `beverage_items`
- `flavor_profiles`
- `recommendation_vectors`

If scoring changes:

```text
Insert a new scoring_configs row such as:
name = default_scoring
version = scoring_v2
target_type = beverage
category = all
```

Rollback:

```text
Set ACTIVE_SCORING_CONFIG back to scoring_v1 and keep evaluation artifacts for
comparison.
```

## 7. API Plan

No public API/protobuf change is planned.

Public RPC behavior:

```text
RecommendationService.GetBeverageRecommendations remains unchanged.
```

Internal/local command:

```text
Endpoint/RPC: none
Caller: developer/CI/operator
Auth: local runtime only
Request: fixture path, limit, scoring config version
Response: console summary and JSON evaluation report
Errors: non-zero exit if configured quality threshold fails
Idempotency: deterministic for the same DB, fixtures, and scoring config
Audit: report includes generated_at, catalog source version, vector schema,
scoring config, and metrics
```

## 8. Migration Plan

No schema migration is planned.

Type:

```text
data/config addition only if scoring_v2 is introduced
```

Production risk:

```text
Medium if active scoring changes. Low if this is evaluation/reporting only.
Use evaluation reports before changing ACTIVE_SCORING_CONFIG.
```

## 9. Verification Plan

```text
- Unit: evaluation fixtures load and validate required fields.
- Unit: evaluator computes top-k hit rate, category/style match, negative
  violations, and reason-code coverage.
- Unit: deterministic scorer returns stable rankings for golden profiles.
- Unit: scoring_v1 behavior remains unchanged unless scoring_v2 is explicitly
  enabled.
- Integration: evaluation CLI runs against seeded beverages.
- Regression: existing recommendation gRPC tests pass.
- Boundary: no survey-service or map-service database access.
- General: ruff, pytest, compileall, git diff --check.
```

## 10. Acceptance Criteria

The task is complete when:

```text
- [x] Drink recommendation evaluation fixtures exist.
- [x] Evaluation CLI produces deterministic JSON metrics.
- [x] Golden profile tests cover major beverage categories and taste traits.
- [x] Recommendation logs expose model-ready feature/debug metadata.
- [x] Any scoring change is versioned, not silently applied to scoring_v1.
- [x] Existing gRPC response contract remains unchanged.
- [x] No live map-service or survey-service dependency is introduced.
- [x] Relevant tests and boundary checks pass.
```

## 11. Risks

```text
- Risk: synthetic fixtures overfit the recommender before real users exist.
  Mitigation: label them as evaluation_v1 and treat metrics as guardrails, not
  proof of product-market quality.

- Risk: a learned model is introduced before enough feedback exists.
  Mitigation: keep production ranking deterministic until recommendation
  interactions provide enough training labels.

- Risk: scoring changes break reproducibility.
  Mitigation: version scoring configs and include scoring version in every
  evaluation report and recommendation log.

- Risk: evaluation ignores future store distance and price.
  Mitigation: scope this plan to drink-only ranking; venue distance and price
  ranking remains a separate map-service-dependent plan.
```
