# Route-Ready Venue Distance Foundation

## 1. Goal

Make selected-beverage venue recommendations ready for future map-service route
integration while keeping the current MVP behavior deterministic.

The immediate technical goal is:

```text
venue ranking uses an explicit distance feature contract
instead of hardcoding haversine distance inside scoring
```

This lets the current service continue using `straight_line_mvp` from venue
snapshot coordinates, while a later map-service integration can provide route
distance, walking time, or route complexity without moving ranking logic into
the gateway, Flutter, chatbot-service, or map-service.

## 2. Non-Goals

- Do not call map-service route APIs in this plan.
- Do not implement route optimization.
- Do not implement Kakao route lookup.
- Do not store Kakao response data.
- Do not create or mutate canonical place/menu/inventory/price data.
- Do not read map-service databases.
- Do not change `GetVenueRecommendations` protobuf fields.
- Do not change beverage ranking or chatbot behavior.

## 4. Ownership Analysis

| Data | Owner | This task writes? | This task reads? | Allowed? |
|---|---|---:|---:|---|
| User location request lat/lng | client/authenticated request context | no | yes | yes |
| Canonical place coordinates | map-service/place-service | no | no direct DB read | yes, via snapshots |
| Venue snapshot coordinates | recommendation-service read model | no | yes | yes |
| Route estimate | future map-service API/tool | no | no | not in this plan |
| Recommendation score/logs | recommendation-service | yes | yes | yes |

Boundary decision:

```text
distance feature abstraction only
```

`recommendation-service` still owns ranking and score breakdowns. map-service
will own canonical route/place facts when the API exists.

## 5. Proposed Change

Add a small internal distance feature contract:

```text
VenueDistanceFeature
VenueDistanceProvider
StraightLineVenueDistanceProvider
```

The default provider computes:

```text
strategy = straight_line_mvp
source = venue_snapshot_coordinates
distance_m = haversine(user_lat_lng, venue_snapshot_lat_lng)
confidence = low/medium because this is not route distance
is_route_distance = false
```

`score_venue_candidate` receives or defaults a distance provider. Later,
map-service route integration can pass a provider that returns:

```text
strategy = map_route_estimate_v1
source = map_service_route_api
is_route_distance = true
route_distance_m
route_duration_seconds
route_complexity
```

## 6. API Plan

No protobuf change.

Existing response metadata will be enriched with distance feature details:

```json
{
  "distance_m": 720.0,
  "distance_strategy": "straight_line_mvp",
  "distance_source": "venue_snapshot_coordinates",
  "distance_confidence": 0.45,
  "is_route_distance": false,
  "straight_line_distance_m": 720.0,
  "route_distance_m": null,
  "route_duration_seconds": null,
  "route_complexity": null
}
```

## 7. Recommendation Plan

Hard filters remain the same:

- invalid user coordinates are rejected
- venue snapshots without usable coordinates are excluded
- distance must fit within `radius_m`
- expired inventory/price rules still apply

Scoring still uses:

```text
distance_fit = 1.0 - distance_m / radius_m
```

The meaning of `distance_m` is documented by `distance_strategy` and
`is_route_distance`.

## 9. Acceptance Criteria

```text
- [x] Venue scoring uses a distance feature provider contract.
- [x] Default behavior remains straight-line MVP distance.
- [x] Source metadata distinguishes straight-line distance from route distance.
- [x] Tests prove future route-like providers can be injected.
- [x] No map-service direct DB access or Kakao route/storage logic is added.
```

## 10. Risks

```text
- Risk: users may interpret straight-line distance as route distance.
  Mitigation: expose `is_route_distance=false`, distance source, strategy, and
  confidence metadata.

- Risk: provider abstraction becomes speculative.
  Mitigation: keep it local to venue scoring and do not add infrastructure,
  network calls, or new services.

- Risk: future map-service route API contract differs.
  Mitigation: adapter/provider can translate the future contract without
  changing recommendation ranking ownership or Flutter response shape.
```
