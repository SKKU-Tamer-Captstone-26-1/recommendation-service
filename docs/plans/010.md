# Staging Integration, Load Test, and MLflow Readiness Plan

## 1. Goal

Move `recommendation-service` from internal beta readiness toward a stronger
production posture by proving real deployed integrations, measuring 500-5,000
user traffic assumptions, and preparing a safe MLflow-based experiment pipeline.

This plan is the next step after `docs/plans/009.md` and
`docs/tech-kr/README.md`.

The goal is to make Flutter integration safer by confirming backend contracts
first:

```text
auth smoke -> survey smoke -> map smoke -> recommendation smoke -> chat smoke
-> load test -> monitoring/exporter -> training dataset export -> MLflow POC
```

## 2. Non-Goals

- Do not ship a learned ranking model to production in this plan.
- Do not replace deterministic `scoring_v1` as the production ranking path.
- Do not use LLM/RAG as the recommendation ranker.
- Do not read survey-service, map-service, place-service, auth-service, or
  chat-service databases directly.
- Do not make Qdrant canonical.
- Do not add Kafka, Airflow, a feature store, or separate ML serving unless a
  later plan proves the need.
- Do not require Flutter changes before backend deployed smokes are proven.
- Do not store Kakao response data as canonical recommendation data.

## 4. Ownership Analysis

| Data | Owner | This plan writes? | This plan reads? | Allowed? |
|---|---|---:|---:|---|
| JWT/JWKS metadata | auth-service | no | API/metadata only | yes |
| Raw survey answers | survey-service | no | API/event only | yes |
| Canonical places/menus/inventory/prices | map-service/place-service | no | snapshot/API only | yes |
| Assistant orchestration | chat-service/assistant-service | no | API smoke only | yes |
| Derived profiles | recommendation-service | yes | yes | yes |
| Map/place read-model snapshots | recommendation-service derived state | yes | yes | yes |
| Recommendation logs/interactions | recommendation-service | yes | yes | yes |
| Operational metrics | recommendation-service | yes | yes | yes |
| Training dataset artifact | recommendation-service derived artifact | yes | yes | yes |
| MLflow experiment metadata | MLflow tracking store | yes | yes | yes |
| Qdrant points | rebuildable derived index | yes | yes | yes |

Boundary decision:

```text
Use deployed service APIs, events, snapshots, and recommendation-owned logs only.
No cross-service database access.
Production ranking remains deterministic until real labels justify a model.
```

Harness boundary answers:

1. recommendation-service owns derived profiles, recommendation logs, metrics,
   catalog/vector state, training exports derived from its own logs, and local
   smoke/load-test artifacts.
2. recommendation-service may write those recommendation-owned records and
   artifacts.
3. recommendation-service must not directly read another service database.
4. Auth/survey/map/chat work must be API, event, metadata, or snapshot based.
5. Admin Page is not involved.
6. This plan does not store Kakao response data.
7. Recommendation reproducibility is affected only by logging/exporting; any
   future model or scoring change must be versioned.
8. RAG boundaries are unchanged; assistant may use recommendation facts, but
   RAG/LLM must not rank.

## 5. Proposed Change

Implement this plan in five separately reviewable slices.

Implementation readiness gate:

```text
service boundary | integration contract | observability contract |
load contract | ML data contract | rollback contract
```

### Slice 1: Staging Integration Smoke Harness

Purpose:

- Prove backend service-to-service contracts before Flutter depends on them.

Work:

- Add environment-driven deployed smoke commands for:
  - auth metadata/JWKS verification
  - survey-service event/response sync
  - map-service/place-service snapshot sync
  - recommendation beverage and venue request
  - chat-service/assistant recommendation orchestration
- Keep local fake/protocol smokes as default tests.
- Require deployed smoke commands to skip clearly when endpoint/credential env
  vars are missing.
- Update `docs/human-effort.md` as blockers are resolved.

Acceptance gate:

```text
auth_deployed_smoke = pass
survey_sync_deployed_smoke = pass
map_snapshot_deployed_smoke = pass
recommendation_deployed_smoke = pass
chat_recommendation_deployed_smoke = pass
no_direct_cross_service_db_access = pass
```

Rollback:

```text
Disable deployed smoke jobs and continue using local fake/protocol smokes.
Do not weaken service boundaries to make a smoke pass.
```

### Slice 2: Load Test Harness for 500-5,000 Users

Purpose:

- Replace guessing with measured traffic limits for the current architecture.

Work:

- Add load-test scripts under `scripts/load/` or `load/` for:
  - `GetProfileStatus`
  - `GetBeverageRecommendations`
  - `GetVenueRecommendations`
  - `RecordRecommendationEvent`
  - mixed traffic
- Prefer `ghz` for gRPC and/or `k6` for gateway/HTTP paths.
- Define profiles:
  - smoke: 1-5 RPS
  - beta: 20 RPS
  - peak: 50 RPS
  - stress: 100 RPS
  - soak: expected peak for 1-2 hours
- Record result reports in `docs/operations/load-tests/`.

Acceptance gate:

```text
load_smoke_script_exists = pass
20_rps_beta_profile_documented = pass
50_rps_peak_profile_documented = pass
100_rps_stress_profile_documented = pass
result_template_exists = pass
```

Quality target:

```text
beverage_recommendation_p95 <= 500ms
venue_recommendation_p95 <= 800ms
error_rate <= 1%
db_connection_saturation = false
qdrant_failure_count = 0
recommendation_empty_rate_spike = false
```

Rollback:

```text
Load-test scripts must not mutate production data unless an explicit safe test
user and safe environment are configured.
```

### Slice 3: Production Metrics Exporter

Purpose:

- Move from local operational metrics to production monitoring.

Work:

- Extend the current `/v1/operations/metrics` surface into one of:
  - Prometheus text endpoint
  - OpenTelemetry metrics
  - both, if the deployment already supports them
- Add latency histograms for recommendation paths.
- Add gRPC status/error counters.
- Add DB pool/connection and Qdrant latency metrics where feasible.
- Add alert rule documentation and Grafana dashboard skeleton.

Acceptance gate:

```text
prometheus_or_otel_exporter = pass
recommendation_latency_histogram = pass
grpc_status_counter = pass
sync_lag_metric = pass
qdrant_failure_metric = pass
dashboard_doc = pass
alert_rule_doc = pass
```

Rollback:

```text
Metrics exporter failure must not block recommendation serving.
Keep `/health/live` dependency-free.
```

### Slice 4: Training Dataset Export

Purpose:

- Prepare real ML experiments without changing the production ranker.

Work:

- Add an offline export command from recommendation-owned data:

```text
python3 -m app.tools.export_training_dataset --from <time> --to <time> --output <path>
```

- Source only:
  - `recommendation_requests`
  - `recommendation_results`
  - `recommendation_explanations`
  - `recommendation_interactions`
  - derived profile metadata
  - map/place read-model snapshot metadata stored in recommendation logs
- Do not export raw survey answers from survey-service.
- Do not query map-service or survey-service databases.
- Emit:
  - dataset manifest
  - feature schema
  - label definitions
  - data quality report
  - deterministic hash
- Prefer Parquet when dependency policy is approved; otherwise start with JSONL
  and document the migration to Parquet.

Acceptance gate:

```text
dataset_export_command = pass
feature_schema_version = pass
label_definition_doc = pass
dataset_manifest_hash = pass
no_raw_survey_export = pass
no_cross_service_db_access = pass
```

Rollback:

```text
Delete generated artifacts only. Do not delete recommendation logs.
```

### Slice 5: MLflow Proof of Concept

Purpose:

- Introduce ML lifecycle discipline before introducing any production model.

Work:

- Add local/staging MLflow tracking guidance or a minimal optional compose
  service only if approved.
- Keep the MLflow backend store separate from recommendation-service schema.
- Log deterministic `scoring_v1` as the baseline run.
- Train or simulate a simple candidate model only offline:
  - logistic regression
  - linear model
  - LightGBM/XGBoost ranker if dependency policy is approved
- Store artifacts:
  - dataset manifest
  - feature schema
  - training config
  - evaluation report
  - model card
- Register the model as `candidate` only.
- Do not enable model serving or production ranking.

Acceptance gate:

```text
mlflow_baseline_run = pass
candidate_model_run = pass
evaluation_report_artifact = pass
model_card_artifact = pass
model_registry_candidate_only = pass
production_ranker_unchanged = pass
```

Rollback:

```text
Disable MLflow experiment jobs. Deterministic `scoring_v1` remains the production
ranker.
```

## 6. Database Plan

Prefer no schema migration for slices 1-3.

Potential additive migrations for slices 4-5 only if JSON metadata becomes
insufficient:

```text
model_shadow_scores
  Purpose: store deterministic rank vs future model rank in shadow mode.
  Owner: recommendation-service.
  Timing: not required for first MLflow POC.

training_dataset_exports
  Purpose: track dataset export manifests and hashes.
  Owner: recommendation-service.
  Timing: optional; a manifest artifact may be enough first.
```

Rules:

- Additive migrations only.
- Do not store raw survey answers.
- Do not store map-service canonical rows beyond approved snapshot metadata.
- Do not delete recommendation logs.

## 7. API Plan

No public protobuf change is required for the first implementation.

Possible internal additions:

```text
GET /v1/operations/metrics/prometheus
  Caller: monitoring system
  Auth: internal network or service auth
  Response: Prometheus text format
  Failure rule: must not affect serving
```

Deployed smoke tools should use environment variables rather than hard-coded
URLs or secrets.

```text

- [ ] Dashboard and alert rules are documented.

- [ ] Production ranking remains deterministic unless a later reviewed plan

```

## 11. Risks

```text
- Risk: Flutter integration hides backend contract failures.
  Mitigation: deployed backend smokes must pass before Flutter is treated as the
  integration test source of truth.

- Risk: load tests mutate real user data.
  Mitigation: require safe test users, safe environment, idempotency keys, and
  explicit target environment variables.

- Risk: metrics exporter adds serving latency.
  Mitigation: keep exporter lightweight and non-blocking.

- Risk: MLflow is mistaken for production ML readiness.
  Mitigation: MLflow POC is experiment tracking only; production ranker remains
  deterministic.

- Risk: training data accidentally crosses service ownership boundaries.
  Mitigation: export only recommendation-owned logs, derived profiles, and stored
  snapshot metadata.
```
