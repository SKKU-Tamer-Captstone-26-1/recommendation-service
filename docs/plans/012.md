# Deployed Survey Wiring and Recommendation GCP Deployment Plan

## 1. Goal

Wire the deployed `survey-service` into `recommendation-service` through the
approved service API contract, prove that completed surveys generate correct
derived recommendation profiles, and then deploy `recommendation-service` to GCP
for Flutter integration.

User-provided deployed survey URL:

```text
https://survey-service-44649239380.asia-northeast3.run.app
```

GCP project inspection on 2026-05-27 showed the Cloud Run service named
`survey-service` also reports:

```text
https://survey-service-vcuepibcwq-du.a.run.app
```

Both URLs returned Cloud Run `502 protocol error` for HTTP smoke paths during
initial planning checks. A gRPC probe against the Cloud Run-reported URL
confirmed the service is reachable over gRPC:

```text
grpcurl survey-service-vcuepibcwq-du.a.run.app:443 grpc.health.v1.Health/Check
=> SERVING
```

Reflection lists:

```text
ontheblock.survey.v1.SurveyService.GetSurveyQuestions
ontheblock.survey.v1.SurveyService.GetSurveyResult
ontheblock.survey.v1.SurveyService.GetSurveyResultByUser
ontheblock.survey.v1.SurveyService.SubmitSurvey
```

The deployed service does not currently expose the recommendation sync RPCs
documented in `docs/recommendation/sync-flow.md`:

```text
ListSurveyEvents
GetSurveyResponse
```

That means deployed protocol/health is now partly confirmed, but production
survey sync is still blocked on an approved event/response contract or an
explicit adapter decision.

Implementation progress:

- `app.tools.deployed_smoke --mode survey` can verify deployed gRPC health via
  `SURVEY_SMOKE_GRPC_ADDR`.
- A controlled one-shot adapter exists for `GetSurveyResult` and
  `GetSurveyResultByUser` so operators can generate a derived profile for a
  safe test user while the cursor-based sync contract is pending.
- The adapter maps `ontheblock.survey.v1.SurveyResult` into the existing
  `survey_v1` mapper shape. It is not a production event sync replacement
  because the deployed service does not provide cursor, event ID, response
  revision, retry, or revocation semantics.
- A guarded Cloud Run gRPC deployment script exists at
  `scripts/deploy/gcp-cloud-run-grpc.sh`. It refuses obvious shared-service
  database secrets and deploys `python -m app.grpc.main` on Cloud Run port 8080
  when recommendation-owned PostgreSQL and Qdrant configuration are provided.

  `ontheblock-chat-staging`; those must not be used for recommendation data.

  still gated on recommendation-owned infrastructure.
- A guarded staging Cloud SQL provisioning script exists at
  `scripts/deploy/gcp-provision-staging-sql.sh`. It can create or confirm the
  recommendation-owned Cloud SQL instance, database, user, and
  `recommendation-db-dsn-staging` secret when
  `RECOMMENDATION_PROVISION_APPLY=1` is explicitly set.
- The provisioning dry-run on 2026-05-27 initially reported the recommendation
  Cloud SQL instance, database, user, and database secret were missing.
- Apply mode on 2026-05-27 created
  `recommendation-postgres-staging`, database `recommendation_service`, user
  `recommendation_user`, and Secret Manager secret
  `recommendation-db-dsn-staging`.
- Post-create dry-run on 2026-05-27 reports instance, database, user, and secret

- The provisioning script explicitly sets Cloud SQL Enterprise edition so the

- A guarded staging Qdrant Cloud Run provisioning script exists at

- Qdrant provisioning dry-run on 2026-05-27 reports the staging service account,

- Apply mode on 2026-05-27 created Cloud Run service
  `recommendation-qdrant-staging`, service account
  `recommendation-qdrant-staging`, and secrets
  `recommendation-qdrant-url-staging` and
  `recommendation-qdrant-api-key-staging`.
- Post-create dry-run on 2026-05-27 reports the Qdrant service account, API key
  secret, Cloud Run service, and URL secret all exist.
- Staging Qdrant HTTPS/API-key smoke passes with the application
  `qdrant-client` factory after fixing the factory to stop forcing default port

- A guarded runtime IAM provisioning script exists at
  `scripts/deploy/gcp-provision-staging-runtime-iam.sh`. It creates a

- Apply mode on 2026-05-27 created
  `recommendation-service-staging@on-the-block-2026.iam.gserviceaccount.com`,

  required DB/Qdrant secrets all exist.
- Recommendation Cloud Run deploy preflight now passes with the
  recommendation-owned DB secret, Qdrant URL/API key secrets, Cloud SQL
  connection name, and runtime service account defaults.

## 2. Non-Goals

- Do not read the survey-service database directly.
- Do not copy or own raw survey answers as recommendation canonical data.
- Do not deploy recommendation-service onto auth-service or chat-service
  databases.
- Do not use Qdrant as canonical storage.
- Do not add Kafka, Redis, Airflow, or separate ML serving in this plan.
- Do not replace deterministic `scoring_v1`.
- Do not implement map-service deployment or canonical map/place ownership.
- Do not wire Flutter directly to survey-service private sync endpoints.

## 4. Ownership Analysis

| Data | Owner | This plan writes? | This plan reads? | Allowed? |
|---|---|---:|---:|---|
| Raw survey answers | survey-service | no | API response only | yes |
| Survey event cursor | recommendation-service | yes | yes | yes |
| Survey sync event state | recommendation-service | yes | yes | yes |
| Derived taste profile | recommendation-service | yes | yes | yes |
| Recommendation vectors | recommendation-service | yes | yes | yes |
| Qdrant points | rebuildable derived index | yes | yes | yes |
| Recommendation logs | recommendation-service | yes | yes | yes |
| Auth identity/JWTs | auth-service | no | metadata/JWKS only | yes |
| Canonical map/place data | map-service/place-service | no | no direct read | yes |
| Flutter client state | Flutter app | no | recommendation API only | yes |

Boundary decision:

```text
Survey data is consumed only through deployed service API/gRPC contracts.
Recommendation-owned PostgreSQL stores derived profiles, sync state, vectors,
and recommendation logs. No cross-service database access.
```

Harness boundary answers:

1. survey-service owns raw survey answers and survey response truth.
2. recommendation-service may write derived profile/vector/sync state only.
3. recommendation-service may not read survey-service storage directly.
4. This must be an API/gRPC/event sync, not a direct DB operation.
5. Admin Page is not involved.
6. Kakao API is not involved.
7. Recommendation reproducibility is affected because deployed survey responses
   generate profile revisions and vectors; mapper/vector/scoring versions must
   remain logged.
8. RAG boundaries are unchanged; LLMs cannot rank.

## 11. Risks

```text
- Risk: The deployed survey URL is not the actual service URL or the service is
  gRPC-only while recommendation-service expects HTTP.
  Mitigation: make protocol verification the first gate before wiring env.

- Risk: Survey internal endpoints require Cloud Run IAM rather than bearer JWT.
  Mitigation: document and implement the exact internal auth metadata before
  running deployed sync.

- Risk: recommendation-service is accidentally deployed against auth/chat DB.
  Mitigation: require a dedicated recommendation DB/secret acceptance gate.

- Risk: Flutter starts calling recommendation before profile sync works.
  Mitigation: use GetProfileStatus and a Flutter feature flag until deployed
  survey sync and active profile smoke pass.

- Risk: Qdrant data is unavailable after deploy.
  Mitigation: PostgreSQL remains canonical; Qdrant must rebuild from PostgreSQL.

- Risk: Cloud Run gRPC port/protocol is misconfigured.
  Mitigation: use `GRPC_HOST=0.0.0.0`, `GRPC_PORT=8080`, and verify gRPC health
  before Flutter handoff.
```
