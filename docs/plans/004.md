# Map Snapshot Sync Worker and Smoke Path

## 1. Goal

Implement the production-safe sync path that lets `recommendation-service`
consume map/place snapshots through approved map-service APIs or events only.

The slice must:

- define the exact V1 map snapshot event/page contract
- pull paginated snapshot events from map-service without direct DB access
- import events idempotently into recommendation-owned read-model tables
- advance a recommendation-owned cursor only after a page imports successfully
- provide a smoke path that imports a venue snapshot, calls
  `GetVenueRecommendations`, and verifies logged source revisions
- restart/rebuild local API and gRPC containers so the served runtime includes
  the new recommendation RPC and sync code

## 2. Non-Goals

- Do not create or mutate canonical place, menu, inventory, or price data.
- Do not read map-service/place-service databases directly.
- Do not add Kafka, Redis, Airflow, or a new service.
- Do not use Kakao APIs as a bulk ingestion or canonical data source.
- Do not change recommendation scoring formulas except where needed to preserve
  source snapshot metadata.
- Do not make Qdrant required for map snapshot sync or venue recommendations.

## 4. Ownership Analysis

| Data | Owner | This task writes? | This task reads? | Allowed? |
|---|---|---:|---:|---|
| Canonical places | map-service/place-service | no | API/event snapshot only | yes |
| Canonical menus | map-service/place-service | no | API/event snapshot only | yes |
| Canonical inventory | map-service/place-service | no | API/event snapshot only | yes |
| Canonical prices | map-service/place-service | no | API/event snapshot only | yes |
| Map snapshot cursor | recommendation-service sync state | yes | yes | yes |
| Map snapshot sync events | recommendation-service sync state | yes | yes | yes |
| Venue read-model snapshots | recommendation-service derived state | yes | yes | yes |
| Recommendation logs | recommendation-service | yes | yes | yes |
| User identity | auth-service | no | authenticated context only | yes |

Boundary decision:

```text
API / event / snapshot sync only; no direct map-service database access.
```

## 5. Proposed Change

Use the V1 contract in `docs/recommendation/map-read-model.md`:

```text
GET /internal/v1/recommendation/map-snapshot-events?cursor=<cursor>&limit=<limit>
```

Add a small sync client and worker service:

- `HttpMapSnapshotClient` fetches one page from map-service.
- `MapSnapshotSyncService` reads the current cursor, imports each event with
  `MapSnapshotImportService`, and advances the cursor after successful import.
- A CLI entry point runs the worker once for local or scheduled execution.
- A smoke CLI creates/imports a deterministic venue snapshot, calls the actual
  gRPC servicer method in-process, and verifies source revisions in persisted
  recommendation result logs.

Implementation readiness gate:

```text
service boundary | API contract | sync contract | recommendation contract |
verification contract
```

Rollback:

```text
Disable the sync worker invocation and stop using the smoke CLI. Existing
derived snapshots and logs remain rebuildable recommendation-owned state.
```

## 7. API Plan

Map-service snapshot API:

```text
Endpoint: GET /internal/v1/recommendation/map-snapshot-events
Caller: recommendation-service sync worker
Auth: internal service auth when deployed; local config may run without auth
Request: cursor, limit
Response: events, next_cursor, has_more, snapshot_watermark
Idempotency: event_id
Errors: retry the page; do not advance cursor on partial failure
```

Recommendation gRPC smoke target:

```text
rpc GetVenueRecommendations(GetVenueRecommendationsRequest)
    returns (GetVenueRecommendationsResponse);
```

The gRPC request still resolves user identity from auth context. The smoke path
uses a static auth resolver only for local verification.

## 8. Migration Plan

No schema migration is planned.

Production risk:

```text
The sync worker is additive. If map-service response shape is invalid, the page
fails before cursor advance and can be replayed after the contract issue is
fixed.
```

## 11. Risks

```text
- Risk: map-service later changes event names or payload shape.
  Mitigation: require `contract_version` and fail closed before cursor advance.

- Risk: duplicate events create duplicate read-model rows.
  Mitigation: process by `event_id` and source revision identity.

- Risk: hidden, closed, merged, archived, rejected, or deleted places appear in
  recommendations.
  Mitigation: store snapshots for audit, but rank only active published venues.

- Risk: local smoke data pollutes development fixtures.
  Mitigation: deterministic event IDs and revision IDs make reruns idempotent.
```
