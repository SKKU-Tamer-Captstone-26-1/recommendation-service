# 70 Percent Production Readiness Plan

## 1. Goal

Move `recommendation-service` from roughly 35% production readiness to a
credible 70% production-readiness level for an internal beta / MVP launch.

For this repository, 70% production means:

- drink recommendations are deterministic, explainable, and quality-gated
- the beverage catalog is broad enough for real MVP users
- PostgreSQL remains canonical and Qdrant is rebuildable
- survey and map integrations work through approved APIs, events, or snapshots
- distance, price, availability, and freshness are ranked from structured
  snapshots, not guessed by an LLM
- core operational checks, runbooks, and rollback paths exist
- a future learned model has clean feature and interaction data, but production
  ranking is still deterministic until real labels exist

## 2. Non-Goals

- Do not claim full production maturity or autonomous ML quality.
- Do not train or deploy a learned ranking model before enough real user
  feedback exists.
- Do not use an LLM or RAG as the recommendation ranking engine.
- Do not read or write survey-service or map-service databases directly.
- Do not make Qdrant canonical.
- Do not add Kafka, Redis, Airflow, feature stores, or separate ML serving for
  this milestone.
- Do not build canonical map/place/menu/inventory/price ownership in this repo.
- Do not store Kakao API responses as canonical place data.

## 4. Ownership Analysis

| Data | Owner | This plan writes? | This plan reads? | Allowed? |
|---|---|---:|---:|---|
| Beverage catalog rows | recommendation-service | yes | yes | yes |
| Flavor profiles | recommendation-service | yes | yes | yes |
| Recommendation vectors | recommendation-service PostgreSQL | yes | yes | yes |
| Scoring configs | recommendation-service | yes | yes | yes |
| Recommendation logs / interactions | recommendation-service | yes | yes | yes |
| Qdrant collections | rebuildable derived index | yes | yes | yes |
| Raw survey answers | survey-service | no | API only | yes |
| Canonical place/menu/inventory/price | map-service/place-service | no | snapshot/API only | yes |
| Map/place read-model snapshots | recommendation-service derived state | yes | yes | yes |
| Auth identity | auth-service | no | auth context only | yes |
| Kakao response data | Kakao / map-service policy | no | no | yes |

Boundary decision:

```text
recommendation-owned data + approved survey/map APIs/snapshots only.
No cross-service database access.
```

Harness boundary answers:

1. Canonical beverage, vector, scoring, log, and read-model state changed here
   is owned by recommendation-service.
2. recommendation-service may write this data.
3. recommendation-service must not directly read survey-service or map-service
   databases.
4. Survey data must be consumed through survey-service APIs/events. Map data
   must be consumed through map-service/place-service APIs, events, or snapshots.
5. Admin Page is not involved in this plan.
6. This plan does not store Kakao API response data.
7. Recommendation reproducibility is affected, so every scoring/catalog/vector
   change must be versioned or source-hashed.
8. RAG boundaries are unaffected; RAG/LLM cannot rank.

## 5. Proposed Change

Implement the 70% target in six slices. Each slice should be committed and
reviewed separately.

Implementation readiness gates:

```text
service boundary | database contract | sync contract | recommendation contract |
verification contract
```

### Slice 1: Commit and Stabilize Plans 007/008

Purpose:

- Treat catalog audit and offline drink evaluation as the foundation for all
  further quality work.

Work:

- Review and commit the plan 007/008 implementation.
- Keep the new audit and evaluation CLIs deterministic.
- Make generated report paths stable for CI or operator use.
- Document current audit warnings and decide which warnings block promotion.

Acceptance gate:

```text
- pytest passes
- ruff passes
- compileall passes
- git diff --check passes
- catalog audit has 0 critical issues
- drink evaluation has 0 negative violations
```

### Slice 2: Expand the Beverage Catalog to MVP Coverage

Purpose:

- Move the drink database from a seed demo to a useful MVP catalog.

Work:

- Expand active approved beverages from 24 to 50-75 records using the existing
  candidate files before collecting new external data.
- Prioritize coverage across whiskey, wine, beer, cocktail, soju, makgeolli,
  sake, liqueur, low-ABV, and non-alcoholic / soft drink options if the product
  needs them.
- Fix known catalog audit warnings for missing aliases and weak reason hints.
- Require every active beverage to have:
  - stable `catalog_key`
  - category and style
  - Korean and English display fields where available
  - tags and aliases
  - `taste_v1` dimension values
  - dimension confidence
  - source metadata and source hash
  - reason-code hints
- Keep source facts in candidate/source artifacts. Do not invent flavor claims
  without confidence and review metadata.

Quality target:

```text
active_beverages >= 50
critical_audit_issues = 0
alias_coverage >= 0.95
reason_code_coverage >= 0.95
style_coverage = 1.0
source_metadata_coverage = 1.0
complete_vector_coverage = 1.0
```

Rollback:

```text
Deactivate newly promoted beverages or restore the previous seed manifest.
Existing deterministic IDs and source hashes must make rollback auditable.
```

### Slice 3: Calibrate Deterministic Drink Ranking

Purpose:

- Improve recommendation precision without pretending we have a trained AI model.

Work:

- Expand evaluation fixtures from 6 to at least 20 realistic profiles.
- Cover beginner, enthusiast, expert, budget-sensitive, low-ABV, sweet, bitter,
  smoky, fruity, acidic, herbal, creamy, Korean alcohol, and soft drink cases.
- Add category/style, positive, negative, and reason-code expectations for each
  fixture.
- Compare current `scoring_v1` against candidate `scoring_v2`.
- Introduce `scoring_v2` only if it improves evaluation metrics without hiding
  regressions.
- Include model-ready features in logs and evaluation reports, but keep the
  serving ranker deterministic.

Quality target:

```text
fixture_count >= 20
top_5_hit_rate >= 0.85
negative_violation_count = 0
average_category_style_match_rate >= 0.65
average_reason_code_coverage >= 0.95
positive_score_above_negative_rate >= 0.90
```

Rollback:

```text
Keep `scoring_v1` as the active config unless `scoring_v2` is explicitly
promoted. To roll back, set active scoring config back to `scoring_v1`.
```

### Slice 4: Harden Postgres, Qdrant, and Rebuild Operations

Purpose:

- Make recommendation state recoverable and operationally testable.

Work:

- Add local integration smoke for:
  - Alembic upgrade
  - beverage import
  - catalog audit
  - Qdrant index
  - Qdrant rebuild
  - recommendation query after rebuild
- Prove Qdrant can be dropped and rebuilt entirely from PostgreSQL vectors.
- Add idempotency checks for repeated import/index/rebuild commands.
- Store enough metadata to compare source hashes and payload hashes.
- Ensure recommendation behavior degrades to PostgreSQL ranking when Qdrant is
  unavailable.

Quality target:

```text
qdrant_rebuild_from_postgres = pass
import_idempotency = pass
index_idempotency = pass
recommendation_without_qdrant = pass
recommendation_after_qdrant_rebuild = pass
```

Rollback:

```text
Disable Qdrant-backed retrieval and serve PostgreSQL-hydrated deterministic
ranking while rebuilding Qdrant.
```

### Slice 5: Integrate Survey and Map Contracts Safely

Purpose:

- Make the recommendation service useful with real platform data without
  coupling to another service database.

Survey work:

- Generate or implement the final survey-service client contract when the
  deployed proto/API is available.
- Keep fake/protocol clients for deterministic tests.
- Add deployed-service smoke only after the endpoint and auth metadata are
  confirmed.
- Persist cursor, retries, last error, dead-letter reason, and replay metadata.

Map work:

- Validate the map snapshot event contract against real map-service output when
  deployed.
- Import venue, menu, inventory, and price snapshots into read-model tables.
- Preserve place, inventory, and price revisions in recommendation logs.
- Enforce freshness and confidence rules.
- Implement selected-beverage venue options:
  - `nearest_reasonable`
  - `best_price`
  - `balanced_best`

Quality target:

```text
survey_sync_fake_e2e = pass
survey_sync_deployed_smoke = pass when service is available
map_snapshot_fake_e2e = pass
map_snapshot_deployed_smoke = pass when service is available
venue_recommendation_logs_include_revisions = pass
no_direct_cross_service_db_access = pass
```

Rollback:

```text
Disable sync workers and continue serving the latest valid local derived state.
Mark stale profiles or venue snapshots with typed statuses instead of inventing
fresh recommendations.
```

### Slice 6: Production Operations, Security, and Release Gate

Purpose:

- Make the service operable by a small team during beta.

Work:

- Add a CI gate or documented local release gate that runs:
  - `pytest`
  - `ruff`
  - `compileall`
  - Alembic upgrade check
  - catalog audit
  - drink evaluation threshold check
  - boundary scan
- Confirm JWT/JWKS verification through auth-service metadata.
- Ensure gRPC handlers do not trust client-supplied `user_id` when authenticated
  context exists.
- Add structured logs for request ID, profile revision, scoring config, vector
  schema, catalog source version, map snapshot revisions, and error type.
- Add minimal metrics for request count, latency, profile missing rate,
  sync lag, audit failures, Qdrant failures, and recommendation empty rate.
- Add runbooks for:
  - catalog import rollback
  - scoring config rollback
  - Qdrant rebuild
  - survey sync replay
  - map snapshot replay
  - stale venue data handling

Quality target:

```text
release_gate = pass
auth_context_smoke = pass
structured_logs_present = pass
runbooks_present = pass
rollback_steps_documented = pass
```

Rollback:

```text
Each release must be reversible by disabling new scoring/config/sync behavior
without deleting PostgreSQL canonical recommendation state.
```

## 6. Database Plan

Prefer no schema changes until repeated query, uniqueness, or operational needs
prove them necessary.

Potential additive migrations:

```text
beverage_items.catalog_key
  Reason: enforce natural-key uniqueness after metadata audit proves stable keys.

recommendation_interactions feature/debug columns or JSON hardening
  Reason: improve model-ready label and feature capture.

sync/run metadata fields
  Reason: only if existing sync tables cannot represent deployed API replay.
```

Rules:

- Additive migrations only.
- Update `docs/database/erd.md` before or with schema changes.
- PostgreSQL remains canonical.
- Qdrant remains disposable.
- Rollback must not require deleting recommendation logs.

## 7. API Plan

No public protobuf change is required for slices 1-4.

Possible API changes for slices 5-6:

```text
Selected beverage venue recommendations may need request fields for trade-off
mode, radius, budget behavior, and location context if existing proto fields are
insufficient.
```

Before any protobuf change:

- Update `docs/api/recommendation-api.md`.
- Regenerate gRPC code.
- Add contract tests.
- Preserve backwards-compatible fields where possible.
- Do not accept untrusted client `user_id` when auth metadata exists.

## 8. Migration Plan

Migration type:

```text
Mostly no migration. Any required schema changes must be additive.
```

Production risk:

```text
Medium. Catalog, scoring, sync, and map freshness changes affect user-visible
recommendations. Risk is controlled by versioned configs, deterministic audits,
offline evaluation, and rollback to previous active scoring/catalog state.
```

## 10. Acceptance Criteria

The service can honestly be called 70% production-ready when:

```text
- [ ] Plans 007 and 008 are committed and passing verification.
- [ ] Active reviewed beverage catalog has at least 50 approved records.
- [ ] Catalog audit has 0 critical issues.
- [ ] Catalog audit warning coverage targets are met or documented as accepted
      beta risk.
- [ ] Offline drink evaluation has at least 20 realistic fixtures.
- [ ] Drink evaluation meets top-5, category/style, negative, and reason-code
      thresholds.
- [ ] Any scoring change is introduced as a versioned config.
- [ ] Qdrant can be rebuilt from PostgreSQL with a passing smoke test.
- [ ] Recommendation serving does not require Qdrant to be available.
- [ ] Survey sync passes fake/protocol e2e tests and deployed smoke when the
      survey-service endpoint is available.
- [ ] Map snapshot sync passes fake/protocol e2e tests and deployed smoke when
      the map-service endpoint is available.
- [ ] Selected-beverage venue recommendations return differentiated
      `nearest_reasonable`, `best_price`, and `balanced_best` options.
- [ ] Recommendation logs include profile revision, scoring config, vector
      schema, score breakdown, reason codes, and map snapshot revisions when
      relevant.
- [ ] Release gate runs tests, lint, compile, migration, audit, evaluation, and
      boundary checks.
- [ ] Rollback runbooks exist for catalog, scoring, Qdrant, survey sync, and map
      sync.
```

## 11. Risks

```text
- Risk: 70% is misunderstood as fully production-ready.
  Mitigation: define it as controlled beta readiness, not full public launch.

- Risk: synthetic evaluation overfits before real users exist.
  Mitigation: keep fixtures diverse and treat them as regression gates, not
  proof of final model quality.

- Risk: catalog expansion introduces inaccurate flavor metadata.
  Mitigation: require source metadata, confidence, audit reports, and operator
  review before active use.

- Risk: survey-service or map-service deployment blocks real integration.
  Mitigation: complete fake/protocol e2e now and add deployed smoke immediately
  when endpoints are available.

- Risk: distance and price ranking becomes misleading from stale data.
  Mitigation: enforce freshness, confidence, and explicit stale-result behavior.

- Risk: learned-model work starts too early.
  Mitigation: collect feature logs and interactions first; keep deterministic
  serving until real labels justify model training.
```
