# Feedback Labels, Shadow Model, and ML Promotion Readiness Plan

## 1. Goal

Move from Plan 010 experiment readiness to a real ML readiness path without
pretending the service already has enough production labels for an autonomous
model.

The goal is to make the next implementation collect reliable recommendation
feedback, export leak-safe training data, train/evaluate a candidate model
offline, and compare it in shadow mode while deterministic `scoring_v1` remains
the production ranker.

This plan is the next step after `docs/plans/010.md`.

Production principle:

```text
collect labels -> validate data quality -> train candidate -> shadow compare
-> human review -> later canary plan
```

## 2. Non-Goals

- Do not replace deterministic production ranking in this plan.
- Do not serve a learned model from the live recommendation path.
- Do not use LLM/RAG as a ranking model.
- Do not read auth-service, survey-service, map-service, place-service, or
  chat-service databases directly.
- Do not store raw survey answers in training exports.
- Do not make Qdrant or MLflow canonical.
- Do not add Kafka, Airflow, a separate feature store, or separate ML serving.
- Do not add public Flutter/API surface unless the existing event contract is
  insufficient.
- Do not claim "real AI model in production" until label volume, offline
  evaluation, shadow evaluation, and rollback gates pass.

## 4. Ownership Analysis

| Data | Owner | This plan writes? | This plan reads? | Allowed? |
|---|---|---:|---:|---|
| Auth identity and JWTs | auth-service | no | metadata only | yes |
| Raw survey answers | survey-service | no | no | yes |
| Derived taste profiles | recommendation-service | no schema change expected | yes | yes |
| Beverage catalog and vectors | recommendation-service | no | yes | yes |
| Recommendation requests/results/explanations | recommendation-service | no schema change expected | yes | yes |
| Recommendation interactions | recommendation-service | yes | yes | yes |
| Map/place read-model snapshots in logs | recommendation-service derived state | no | yes | yes |
| Canonical places/menus/inventory/prices | map-service/place-service | no | no direct DB read | yes |
| Training dataset artifacts | recommendation-service derived artifact | yes | yes | yes |
| MLflow experiment artifacts | MLflow tracking/artifact store | yes | yes | yes |
| Shadow model scores | recommendation-service derived evaluation state | yes | yes | yes |
| Qdrant points | rebuildable derived index | no | optional read only | yes |

Boundary decision:

```text
Use recommendation-owned logs, derived profile metadata, catalog vectors, and
stored map snapshot metadata only. No cross-service database reads.
```

Harness boundary answers:

1. recommendation-service owns recommendation interactions, derived training
   artifacts, and shadow evaluation records.
2. recommendation-service may write those records and artifacts.
3. recommendation-service must not read raw survey answers or external service
   databases.
4. Survey/map/auth/chat dependencies remain API, event, metadata, or snapshot
   based.
5. Admin Page is not involved.
6. Kakao API is not involved.
7. Recommendation reproducibility is affected, so feature schema, dataset hash,
   candidate model run ID, and shadow scoring version must be stored.
8. RAG boundaries are unchanged; LLMs cannot rank.

## 5. Proposed Change

Implement this plan in six separately reviewable slices.

Implementation readiness gate:

```text
feedback contract | label quality contract | feature contract |
offline model contract | shadow contract | promotion contract |
rollback contract
```

### Slice 1: Feedback Event Contract Hardening

Purpose:

- Make product feedback reliable enough to become training labels.

Work:

- Align gRPC enum handling, service validation, export labels, and docs for:
  - impression
  - click
  - save
  - dismiss
  - detail view
- Ensure `RECOMMENDATION_EVENT_TYPE_IMPRESSION` is accepted by the gRPC service
  if the proto already exposes it.
- Require idempotency keys for client-generated feedback in staging and
  production guidance.
- Define allowed event metadata keys:
  - client_platform
  - app_version
  - surface
  - session_id_hash
  - list_position
  - visible_ms
  - source
- Reject or strip PII-like metadata from feedback events.
- Add tests for duplicate events, unsupported events, impression events, and
  metadata safety.
- Update `docs/api/recommendation-api.md` and
  `docs/operations/training-dataset.md`.

Acceptance gate:

```text
feedback_event_contract_documented = pass
impression_event_supported_or_explicitly_disabled = pass
idempotency_guidance_documented = pass
metadata_allowlist_tested = pass
duplicate_event_test = pass
no_pii_feedback_metadata = pass
```

Rollback:

```text
Disable new metadata validation or impression ingestion while preserving
existing click/save/dismiss/detail_view interactions.
```

### Slice 2: Label Quality Audit

Purpose:

- Detect whether collected labels are usable before training a model.

Work:

- Add a label quality audit command:

```bash
python3 -m app.tools.audit_training_labels \
  --from <time> \
  --to <time> \
  --report <path>
```

- Report:
  - request count
  - result count
  - impression coverage
  - click-through rate
  - save rate
  - dismiss rate
  - detail-view rate
  - duplicate event rate
  - missing idempotency rate
  - event metadata rejection count
  - positive/negative label ratio
  - label volume by target type
  - user/day and request/day distribution using hashed IDs only
- Add minimum thresholds for "trainable" status.

Initial trainable threshold:

```text
impressions >= 10,000
positive_events >= 500
negative_events >= 500
impression_coverage >= 0.90
missing_idempotency_rate <= 0.01
duplicate_event_rate <= 0.05
```

For local tests, use small fixture thresholds. Production thresholds must stay
documented and stricter.

Acceptance gate:

```text
label_quality_audit_command = pass
trainable_status_computed = pass
production_thresholds_documented = pass
local_fixture_thresholds_tested = pass
no_raw_survey_export = pass
```

Rollback:

```text
Do not train candidate models from periods that fail label quality thresholds.
```

### Slice 3: Leak-Safe Feature Extraction

Purpose:

- Make training features reusable and defensible instead of hidden inside one
  export script.

Work:

- Extract feature generation into a versioned module used by both dataset export
  and model evaluation.
- Add `feature_schema_version = recommendation_features_v1`.
- Include only features known at recommendation time:
  - profile derived vector dimensions
  - request filters
  - candidate category/style/vector metadata
  - deterministic score components
  - venue snapshot distance/price/availability/freshness metadata when present
  - scoring config version
  - mapper version
  - vector schema version
- Exclude post-event features from model inputs:
  - click/save/dismiss/detail_view labels
  - event timestamps after recommendation creation
  - future inventory/price updates
- Add deterministic train/validation split by time window and stable hash.
- Add data quality checks for missing features, null labels, and leakage keys.

Acceptance gate:

```text
feature_extractor_versioned = pass
dataset_export_uses_feature_extractor = pass
leakage_guard_tests = pass
time_based_split = pass
feature_schema_hash = pass
```

Rollback:

```text
Keep Plan 010 JSONL export format and disable candidate training if feature
schema validation fails.
```

### Slice 4: Offline Candidate Ranker

Purpose:

- Train or simulate a candidate ranker offline and compare it against
  deterministic `scoring_v1`.

Work:

- Add a local offline training command:

```bash
python3 -m app.tools.train_candidate_ranker \
  --dataset-export-dir <path> \
  --output <path> \
  --min-positive-labels 500 \
  --min-negative-labels 500
```

- Start with a dependency-light candidate:
  - linear/logistic scoring implemented locally, or
  - optional `scikit-learn` only if dependency policy approves it.
- Compute baseline metrics for deterministic `scoring_v1`.
- Compute candidate metrics:
  - AUC or pairwise preference accuracy when labels allow it
  - top-k hit rate
  - NDCG@5 or MAP@5 when impressions are reliable
  - negative violation rate
  - category/style fairness slices
  - venue distance/price slice quality when venue labels exist
- Emit MLflow-compatible artifacts:
  - training_config.json
  - feature_schema.json
  - dataset_manifest.json
  - baseline_metrics.json
  - candidate_metrics.json
  - evaluation_report.json
  - model_card.md
  - candidate_model.json

Acceptance gate:

```text
offline_training_command = pass
baseline_metrics_recorded = pass
candidate_metrics_recorded = pass
model_card_artifact = pass
candidate_registered_only = pass
production_ranker_unchanged = pass
```

Rollback:

```text
Delete generated training artifacts. Do not delete recommendation logs or
interactions.
```

### Slice 5: Shadow Score Storage and Comparison

Purpose:

- Compare candidate model ordering against live deterministic ranking without
  changing user-visible results.

Work:

- Add additive `model_shadow_scores` table if artifact-only comparison is not
  enough.
- Add a shadow scoring command:

```bash
python3 -m app.tools.shadow_score_candidate \
  --candidate-model <path> \
  --from <time> \
  --to <time> \
  --output <path>
```

- Store enough metadata to reproduce the comparison:
  - candidate model name/version/run ID
  - dataset manifest hash
  - feature schema version/hash
  - baseline scoring config version
  - request ID
  - result ID
  - target type and target ID
  - baseline rank and score
  - candidate rank and score
  - rank delta
  - feature hash
  - created_at
- Add report sections:
  - rank disagreement rate
  - wins/losses/ties against labels
  - price/distance slice impact for venue results
  - category/style slice impact for beverage results
  - examples requiring human review

Acceptance gate:

```text
shadow_score_command = pass
shadow_scores_reproducible = pass
rank_disagreement_report = pass
no_serving_path_change = pass
model_version_logged = pass
```

Rollback:

```text
Disable shadow scoring jobs and drop only the additive shadow table if needed.
Deterministic serving remains unchanged.
```

### Slice 6: Promotion Gate Documentation

Purpose:

- Make the next model decision reviewable before any canary or production
  serving change.

Work:

- Add `docs/operations/model-promotion.md`.
- Define promotion gates:
  - label quality pass
  - offline candidate beats baseline by documented margin
  - no severe slice regressions
  - shadow comparison pass
  - rollback command documented
  - model version and feature schema version logged
  - canary plan reviewed in a later ExecPlan
- Define hard stop conditions:
  - low label volume
  - high duplicate rate
  - missing impression coverage
  - candidate improves average metric but hurts beginner/budget/venue slices
  - external service snapshot freshness is too low

Acceptance gate:

```text
model_promotion_doc = pass
hard_stop_conditions_documented = pass
rollback_doc = pass
canary_deferred_to_next_plan = pass
```

Rollback:

```text
No production model is enabled in this plan, so rollback is disabling training
and shadow jobs.
```

## 6. Database Plan

Additive migration only if Slice 5 stores shadow scores in PostgreSQL.

```text
model_shadow_scores
  id uuid primary key
  request_id uuid not null references recommendation_requests(id)
  result_id uuid null references recommendation_results(id)
  target_type varchar(50) not null
  target_id varchar(128) not null
  baseline_scoring_config_version varchar(80) not null
  baseline_rank int null
  baseline_score float null
  candidate_model_name varchar(120) not null
  candidate_model_version varchar(120) not null
  candidate_run_id varchar(160) not null
  candidate_rank int null
  candidate_score float null
  rank_delta int null
  dataset_manifest_hash varchar(128) not null
  feature_schema_version varchar(80) not null
  feature_schema_hash varchar(128) not null
  feature_hash varchar(128) not null
  shadow_context_json jsonb not null default '{}'
  created_at timestamptz not null
  updated_at timestamptz not null

Indexes:
  ix_model_shadow_scores_request
  ix_model_shadow_scores_result
  ix_model_shadow_scores_candidate_created
  ix_model_shadow_scores_target

Constraints:
  candidate_score between 0 and 1 when the model emits probability
  request/result references remain recommendation-owned

Audit:
  candidate_run_id, dataset_manifest_hash, feature_hash, and created_at provide
  reproducibility.

Lifecycle:
  Shadow scores are derived evaluation state and may be archived or regenerated.

Rollback:
  Drop model_shadow_scores. Do not delete recommendation logs.
```

No schema change is required for raw survey answers, canonical map data, auth
identity, or Qdrant.

## 7. API Plan

Public proto changes should be avoided.

Existing RPC:

```text
RecommendationService.RecordRecommendationEvent
```

Expected changes:

```text
Caller: Flutter/backend clients through gateway
Auth: authenticated user context from gateway metadata
Request: existing request_id, result_id, event_type, idempotency_key, metadata
Response: existing interaction_id and duplicate flag
Errors:
  INVALID_ARGUMENT for unsupported event type or unsafe metadata
  UNAUTHENTICATED when auth metadata is missing
Idempotency:
  idempotency_key required by production guidance for client event writes
Audit:
  recommendation_interactions row with metadata allowlist only
```

If future Flutter needs richer feedback, create a later API plan rather than
overloading free-form metadata.

## 10. Acceptance Criteria

The plan is complete when:

```text
- [ ] Feedback event contract is aligned across proto, gRPC, service, docs, and
      training export.
- [ ] Impression, click, save, dismiss, and detail_view labels are handled
      intentionally.
- [ ] Feedback metadata is allowlisted and PII-like fields are rejected.
- [ ] Label quality audit command exists with production thresholds.
- [ ] Feature extraction is versioned, shared, and leak-safe.
- [ ] Dataset export uses the versioned feature extractor.
- [ ] Offline candidate training/evaluation command emits MLflow-compatible
      artifacts.
- [ ] Candidate model is registered or documented as candidate only.
- [ ] Shadow score comparison exists and stores reproducible metadata.
- [ ] Model promotion gates and hard stop conditions are documented.
- [ ] Production recommendation ranking remains deterministic.
- [ ] No cross-service database access is introduced.
```

## 11. Risks

```text
- Risk: The team trains on weak or biased labels too early.
  Mitigation: label audit must return trainable=false until volume and quality
  thresholds pass.

- Risk: Event metadata leaks user PII.
  Mitigation: allowlist metadata keys and reject obvious PII-like keys.

- Risk: Feature leakage makes offline model metrics look better than reality.
  Mitigation: feature extractor must exclude post-recommendation events and
  future snapshot updates.

- Risk: Candidate model improves average metrics but hurts beginner, budget, or
  venue distance/price slices.
  Mitigation: slice metrics and hard stop conditions block promotion.

- Risk: Shadow scoring becomes a hidden serving dependency.
  Mitigation: shadow jobs are offline/async only and serving path must not read
  model_shadow_scores.

- Risk: Large shadow tables grow without control.
  Mitigation: store only reviewed windows first, document retention, and keep
  shadow scores rebuildable.
```
