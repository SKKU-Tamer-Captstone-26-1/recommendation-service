# Qdrant Indexing and Rebuild Operations

## 1. Goal

Implement the production-safe vector indexing and rebuild slice for
`recommendation-service`.

The slice must:

- index canonical PostgreSQL `recommendation_vectors` into Qdrant
- keep PostgreSQL as the source of truth for all vectors
- treat Qdrant collections as rebuildable and disposable
- persist Qdrant point metadata in `qdrant_points`
- support idempotent upsert/retry for beverage and profile vectors
- provide a rebuild command that can recreate Qdrant collections from PostgreSQL
- add a smoke path proving seed beverage/profile vectors are indexed and
  searchable without changing deterministic ranking semantics

## 2. Non-Goals

- Do not make Qdrant canonical.
- Do not delete PostgreSQL vectors after indexing.
- Do not replace deterministic PostgreSQL ranking with Qdrant-only ranking.
- Do not change `taste_v1` dimensions, mapper logic, or scoring weights.
- Do not add new vector schema versions.
- Do not add Kafka, Redis, Airflow, or distributed workflow infrastructure.
- Do not implement assistant/RAG runtime.
- Do not index raw survey answers or map-service canonical data.

## 4. Ownership Analysis

| Data | Owner | This task writes? | This task reads? | Allowed? |
|---|---|---:|---:|---|
| Beverage catalog rows | recommendation-service | no | yes | yes |
| Profile revisions | recommendation-service | no | yes | yes |
| Recommendation vectors | recommendation-service | no | yes | yes |
| Qdrant collections | rebuildable derived index | yes | yes | yes |
| Qdrant point metadata | recommendation-service | yes | yes | yes |
| Raw survey answers | survey-service | no | no | yes |
| Canonical place/menu/inventory/price | map-service/place-service | no | no | yes |
| Recommendation ranking/logs | recommendation-service | no ranking change | no | yes |

Boundary decision:

```text
PostgreSQL canonical vectors -> Qdrant derived index -> PostgreSQL metadata.
```

Harness boundary answers:

1. Canonical vector data is owned by recommendation-service PostgreSQL.
2. This service may write Qdrant point metadata and derived Qdrant points.
3. This service must not read survey-service or map-service databases.
4. This is an indexing/rebuild operation from owned PostgreSQL state.
5. Admin Page is not involved.
6. No Kakao response data is stored or indexed.
7. Recommendation reproducibility is affected only if ranking starts using
   Qdrant; this slice must keep deterministic PostgreSQL reranking and logs.
8. RAG boundaries are unaffected.

## 5. Proposed Change

Add a Qdrant indexing service around existing canonical
`recommendation_vectors`.

Implementation readiness gate:

```text
service boundary | database contract | vector contract | rebuild contract |
verification contract
```

The smallest useful implementation:

- Add a `VectorIndexingService` that:
  - selects canonical PostgreSQL vectors by owner type and schema
  - validates vector dimension count against `taste_v1`
  - builds deterministic Qdrant point IDs
  - computes payload hashes
  - upserts points to configured Qdrant collections
  - upserts/updates `qdrant_points` rows with `pending`, `indexed`, `failed`,
    `indexed_at`, `last_error`, and payload metadata
- Add a lightweight `QdrantVectorClient` wrapper to isolate Qdrant SDK calls.
- Add a CLI entry point for one-shot indexing:

```text
python -m app.tools.qdrant_index --owner-type beverage_item
python -m app.tools.qdrant_index --owner-type profile_revision
```

- Add a rebuild command:

```text
python -m app.tools.qdrant_rebuild --collection beverage_vectors_v1
```

- Add smoke verification:
  1. ensure beverage seed/profile vectors exist in PostgreSQL
  2. index them into Qdrant
  3. query Qdrant directly for nearest points
  4. verify `qdrant_points.index_status = indexed`
  5. verify recommendation RPC still logs PostgreSQL-derived result metadata

## 6. Database Plan

No new migration is expected for the initial slice.

Existing tables:

- `recommendation_vectors`
- `qdrant_points`
- `vector_schema_versions`
- `beverage_items`
- `taste_profile_revisions`

Required behavior:

```text
recommendation_vectors remains canonical.
qdrant_points is metadata for rebuildable Qdrant points.
Qdrant point payloads are derived from PostgreSQL vector rows.
```

Rollback:

```text
Disable indexing commands/workers and optionally drop/recreate Qdrant
collections. PostgreSQL vectors and recommendation behavior remain available.
```

## 7. API / Runtime Plan

No public API contract changes are planned.

Internal runtime commands:

```text
qdrant_index:
  Inputs: owner_type, collection_name, limit, dry_run
  Output: indexed_count, skipped_count, failed_count
  Idempotency: vector_id + collection_name + payload_hash

qdrant_rebuild:
  Inputs: collection_name, owner_type, vector_schema, confirm flag
  Output: dropped/recreated collection, reindexed counts
  Safety: refuse destructive rebuild without explicit confirm flag
```

Qdrant collection expectations:

| Collection | Owner Type | Source |
|---|---|---|
| `beverage_vectors_v1` | `beverage_item` | `recommendation_vectors` |
| `profile_vectors_v1` | `profile_revision` | `recommendation_vectors` |
| `venue_vectors_v1` | `venue_snapshot` | future slice |
| `menu_item_vectors_v1` | `venue_menu_snapshot` | future slice |

Errors:

| Case | Handling |
|---|---|
| Qdrant unavailable | mark point failed or keep pending; do not delete PG vector |
| vector dimension mismatch | fail fast and do not index point |
| missing vector schema | fail fast |
| collection missing | create collection if configured; otherwise fail |
| payload hash unchanged | skip upsert and keep indexed metadata |

## 8. Migration Plan

No schema migration should be needed.

If implementation proves existing `qdrant_points` cannot represent required
metadata, use an additive migration only after updating `docs/database/erd.md`.

Production risk:

```text
Low to medium. Qdrant is derived, so failures should degrade retrieval breadth
only. Ranking must remain PostgreSQL-hydrated and deterministic.
```

## 9. Verification Plan

```text
- Unit: point ID and payload hash generation are deterministic.
- Unit: vector dimension validation rejects malformed vectors.
- Unit: unchanged payload hash skips duplicate upsert.
- Unit: failed Qdrant upsert marks qdrant_points failed with last_error.
- Integration: fake Qdrant client indexes beverage/profile vectors.
- Smoke: local Qdrant indexes seed vectors and nearest-neighbor query returns
  expected point metadata.
- Regression: beverage and venue recommendation tests still pass without
  requiring Qdrant.
- Boundary: no survey-service or map-service database access.
- General: ruff, pytest, compileall, git diff --check.
```

## 10. Acceptance Criteria

The task is complete when:

```text
- [ ] PostgreSQL recommendation_vectors remain canonical and are never deleted
      by indexing.
- [ ] Qdrant indexing writes derived points from PostgreSQL vectors only.
- [ ] `qdrant_points` metadata is created/updated idempotently.
- [ ] Failed indexing persists `failed` status and `last_error`.
- [ ] Re-running indexing with unchanged payloads does not create duplicate
      Qdrant point metadata.
- [ ] Rebuild command can recreate a configured collection from PostgreSQL.
- [ ] Smoke path proves local Qdrant search works from indexed seed vectors.
- [ ] Recommendation RPC behavior remains deterministic and does not depend on
      Qdrant availability.
- [ ] Relevant tests and boundary checks pass.
```

## 11. Risks

```text
- Risk: Qdrant SDK behavior changes collection creation defaults.
  Mitigation: wrap SDK calls behind a small internal client and test arguments.

- Risk: ranking accidentally depends on Qdrant before hydration/reranking is
  stable.
  Mitigation: keep Qdrant as candidate retrieval only; PostgreSQL still hydrates
  and logs canonical metadata.

- Risk: bad vector dimensions corrupt search quality.
  Mitigation: validate dimension count before indexing and fail fast.

- Risk: destructive rebuild removes useful local data.
  Mitigation: require explicit confirm flag for collection recreation.

- Risk: Qdrant is unavailable in local/dev.
  Mitigation: unit tests use fake client; smoke is the only local Qdrant
  dependency.
```
