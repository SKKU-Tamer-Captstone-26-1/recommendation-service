# Survey Sync Worker and Profile Regeneration

## 1. Goal

Implement the production-safe survey sync path that lets
`recommendation-service` derive user taste profiles from `survey-service`
events and canonical survey responses.

The slice must:

- define the exact SurveyService event/response contract consumed by this
  service
- pull survey events by cursor through a service API or gRPC client only
- fetch canonical survey response revisions through survey-service only
- generate or refresh derived taste profiles idempotently
- persist sync event status, attempts, retry metadata, and dead-letter evidence
- keep recommendation-owned PostgreSQL as the source of truth for derived
  profiles and vectors
- add an end-to-end smoke path: sync a survey response, call recommendation
  gRPC, and verify the recommendation request logs the derived profile revision

## 2. Non-Goals

- Do not read or write the survey-service database directly.
- Do not own or mutate raw survey answers.
- Do not implement survey-service itself.
- Do not trust client-supplied user identity when authenticated metadata exists.
- Do not change taste vector dimensions, mapper semantics, or scoring weights.
- Do not require Qdrant indexing for this slice.
- Do not add Kafka, Redis, Airflow, or distributed workflow infrastructure.
- Do not implement assistant/RAG behavior.

## 4. Ownership Analysis

| Data | Owner | This task writes? | This task reads? | Allowed? |
|---|---|---:|---:|---|
| Raw survey answers | survey-service | no | API response only | yes |
| Survey event stream | survey-service | no | API/gRPC cursor only | yes |
| User identity | auth-service | no | event/auth context only | yes |
| User profile state | recommendation-service | yes | yes | yes |
| Taste profile revisions | recommendation-service | yes | yes | yes |
| Survey source snapshots | recommendation-service generation evidence | yes | yes | yes |
| Recommendation vectors | recommendation-service | yes | yes | yes |
| Qdrant points | rebuildable derived index | no | no | yes |
| Recommendation logs | recommendation-service | yes | yes | yes |

Boundary decision:

```text
survey-service API/gRPC pull sync only; no survey-service database access.
```

Harness boundary answers:

1. Raw survey data is owned by survey-service.
2. Recommendation-service may write only derived profile/vector state.
3. Recommendation-service may not directly read survey-service data stores.
4. This must be an API/event cursor flow, not a direct DB operation.
5. Admin Page is not involved.
6. No Kakao response data is stored or referenced.
7. The change affects recommendation reproducibility, so mapper/vector/scoring
   versions and source response revision must be logged.
8. RAG boundaries are unaffected.

## 5. Proposed Change

Add a survey sync client and worker around the existing deterministic
`ProfileGenerationService`.

Implementation readiness gate:

```text
service boundary | API contract | sync contract | recommendation contract |
verification contract
```

The smallest useful implementation:

- Add a `SurveySyncClient` protocol.
- Add a `GrpcSurveySyncClient` only after the deployed survey-service proto is
  confirmed.
- Add a `SurveySyncService.sync_once(source_name, limit)` that:
  1. reads `survey_sync_cursors`
  2. fetches one event page from survey-service
  3. persists each `survey_sync_events` row by `event_id`
  4. fetches the canonical survey response revision for completed/updated events
  5. calls `ProfileGenerationService.generate_from_survey_input`
  6. marks the event processed
  7. advances the cursor only after the page succeeds
- Make profile generation idempotent for:

```text
external_user_id + survey_response_id + response_revision + mapper_version
```

- Add retry/dead-letter handling for invalid schemas, unsupported survey
  versions, mapper validation errors, and repeated service failures.
- Add a CLI entry point for one-shot local/scheduled sync.
- Add an in-process smoke CLI using a fake survey client to prove the end-to-end
  profile and recommendation path.

## 6. Database Plan

No new migration is expected for the initial slice.

Existing tables:

- `survey_sync_cursors`
- `survey_sync_events`
- `dead_letter_events`
- `user_profile_state`
- `taste_profile_revisions`
- `survey_source_snapshots`
- `recommendation_vectors`
- `recommendation_requests`

Required behavior:

```text
survey_sync_events.event_id is the event idempotency key.
taste_profile_revisions unique profile generation identity prevents duplicate
profile revisions for the same response revision and mapper.
survey_source_snapshots stores redacted generation evidence only.
```

Rollback:

```text
Stop the worker/CLI. Existing derived profile revisions remain audit data and
can be superseded by a later regeneration.
```

## 7. API Plan

Preferred survey-service gRPC contract:

```proto
service SurveyService {
  rpc ListSurveyEvents(ListSurveyEventsRequest)
      returns (ListSurveyEventsResponse);
  rpc GetSurveyResponse(GetSurveyResponseRequest)
      returns (GetSurveyResponseResponse);
}

message ListSurveyEventsRequest {
  string cursor = 1;
  int32 limit = 2;
}

message ListSurveyEventsResponse {
  string cursor = 1;
  string next_cursor = 2;
  bool has_more = 3;
  string event_watermark = 4;
  repeated SurveyEvent events = 5;
}

message SurveyEvent {
  string event_id = 1;
  string event_type = 2;
  google.protobuf.Timestamp occurred_at = 3;
  string external_user_id = 4;
  string survey_response_id = 5;
  string survey_version = 6;
  int32 response_revision = 7;
}

message GetSurveyResponseRequest {
  string survey_response_id = 1;
  int32 response_revision = 2;
}

message GetSurveyResponseResponse {
  string survey_response_id = 1;
  string external_user_id = 2;
  string survey_version = 3;
  int32 response_revision = 4;
  google.protobuf.Timestamp completed_at = 5;
  google.protobuf.Struct answers = 6;
}
```

Supported event behavior:

| Event Type | Behavior |
|---|---|
| `survey.response_completed` | Fetch response, generate active profile. |
| `survey.response_updated` | Fetch response, generate newer active profile. |
| `survey.response_revoked` | Mark profile state stale/unavailable without deleting history. |
| `survey.schema_published` | Process event as metadata/review signal; do not generate profile. |

Auth:

```text
Use internal service credentials when deployed. Local fake clients are allowed
only for tests and smoke.
```

Errors:

| Case | Handling |
|---|---|
| survey-service unavailable | retry event/page; do not advance cursor |
| invalid event shape | dead-letter after configured attempts |
| missing response revision | retry, then dead-letter |
| unsupported survey version | dead-letter with mapper compatibility reason |
| duplicate event | no-op and count as duplicate |
| duplicate profile identity | return existing/generated profile; do not create another active revision |

## 8. Migration Plan

No migration should be needed unless implementation proves existing sync/event
tables cannot represent retry or dead-letter requirements.

If a migration becomes necessary, it must be additive and reviewed before
implementation.

Production risk:

```text
Medium. Bad sync can generate wrong user profiles. Mitigate by failing closed,
storing source revision metadata, keeping mapper versions stable, and making
rebuild possible from survey-service responses.
```

## 9. Verification Plan


## 10. Acceptance Criteria

The task is complete when:

```text
- [x] Survey event/response contract is documented or imported from the real
      survey-service proto.
- [x] Survey sync implementation consumes survey-service API/gRPC only.
- [x] Sync cursor advances only after successful page processing.
- [x] Duplicate event IDs do not regenerate duplicate profiles.
- [x] Duplicate response revisions for the same mapper do not create duplicate
      active profile revisions.
- [x] Completed/updated events generate active profile revisions.
- [x] Revoked events make profile state unavailable or stale without deleting
      history.
- [x] Failure attempts, retry timestamps, last errors, and dead-letter evidence
      are persisted.
- [x] Smoke path proves sync -> profile -> recommendation gRPC -> request log.
- [x] Relevant tests and boundary checks pass.
```

## 11. Risks

```text
- Risk: survey-service proto differs from this planned contract.
  Mitigation: implement the client only after checking the real proto; keep
  tests against a protocol/fake client until then.

- Risk: profile regeneration accidentally creates multiple active revisions for
  the same source response.
  Mitigation: enforce idempotency in service code before creating revisions.

- Risk: revoked survey data remains eligible for recommendations.
  Mitigation: explicitly update user_profile_state and preserve historical
  profile revisions only for audit.

- Risk: raw survey answers are stored too broadly.
  Mitigation: store only the existing redacted generation snapshot and source
  identifiers; survey-service remains canonical.

- Risk: Qdrant indexing failure blocks profile availability.
  Mitigation: keep Qdrant out of this slice; PostgreSQL vectors remain
  canonical.
```
