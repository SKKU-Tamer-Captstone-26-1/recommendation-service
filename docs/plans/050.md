# Plan 050 - Venue Distance Fallback Metadata

## Goal

Make venue recommendation distance evidence safer for production by separating
normal straight-line distance from route-provider fallback distance.

## Problem

Before this slice, request logs counted straight-line distance results as
fallback results. That made two different states look the same:

- map route distance is disabled and the service intentionally uses straight-line
  MVP distance
- map route distance is enabled, route lookup fails, and the service falls back
  to straight-line distance

Flutter, gateway, chatbot-service, and operators need to distinguish those
states before route-style copy or production route coverage metrics can be
trusted.

## Scope

- Add `distance_fallback_used` to per-result venue distance metadata.
- Mark fallback distance only inside `FallbackVenueDistanceProvider`.
- Count `fallback_distance_result_count` from `distance_fallback_used=true`.
- Keep default `StraightLineVenueDistanceProvider` results as non-fallback.
- Validate the field in deployed venue contract smoke.
- Update tests and API/handoff/release-gate docs.

## Non-Goals

- No DB schema change.
- No proto change.
- No scoring weight change.
- No canonical map/place/route ownership change.
- No Flutter, gateway, chatbot, or map-service implementation.
- No model training.

## Acceptance Criteria

- [x] Default straight-line venue results are not counted as fallback.
- [x] Route-aware venue results are not counted as fallback.
- [x] Route-missing/invalid fallback results are counted as fallback.
- [x] Request logs preserve route coverage and fallback counts separately.
- [x] Deployed smoke validates `metadata.source.distance_fallback_used`.
- [x] Focused tests pass.
- [x] Release gate passes.

## Rollback

Rollback is additive metadata only. Remove `distance_fallback_used`, restore
fallback counts to the previous behavior if needed, and remove the smoke/docs
requirements. Existing response fields remain compatible.
