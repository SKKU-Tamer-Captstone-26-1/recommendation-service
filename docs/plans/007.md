# Beverage Catalog Precision and Model-Ready Dataset

## 1. Goal

Improve the recommendation-owned drink database so beverage recommendations are
based on precise, auditable, model-ready catalog data while map-service and
survey-service deployment are still pending.

The slice must:

- make the curated beverage catalog quality measurable
- validate every active drink has complete `taste_v1` vectors and confidence
  metadata
- preserve PostgreSQL as canonical beverage catalog and vector storage
- improve category, style, tag, alias, source, and reason-code metadata
- add a repeatable catalog audit/report path for current seed data
- keep Qdrant as a derived index only
- produce a data foundation that a later learned ranking model can trust

## 2. Non-Goals

- Do not implement map-service or survey-service.
- Do not read map-service, place-service, survey-service, or auth-service
  databases.
- Do not make Qdrant canonical.
- Do not train or deploy a black-box ranking model in this slice.
- Do not use an LLM as the recommendation ranking source.
- Do not change `taste_v1` dimension meanings or order.
- Do not add Kafka, Redis, Airflow, or new services.
- Do not treat venue price or inventory as beverage catalog truth.

## 4. Ownership Analysis

| Data | Owner | This task writes? | This task reads? | Allowed? |
|---|---|---:|---:|---|
| Beverage catalog rows | recommendation-service | yes | yes | yes |
| Flavor profiles | recommendation-service | yes | yes | yes |
| Recommendation vectors | recommendation-service PostgreSQL | yes | yes | yes |
| Source/candidate artifacts | recommendation-service staging evidence | yes | yes | yes |
| Qdrant points | rebuildable derived index | no | no | yes |
| Raw survey answers | survey-service | no | no | yes |
| Canonical venue/menu/inventory/price | map-service/place-service | no | no | yes |
| User identity | auth-service | no | no | yes |

Boundary decision:

```text
recommendation-owned beverage catalog and vector curation only.
```

Harness boundary answers:

1. Canonical data changed is the recommendation-owned beverage catalog.
2. recommendation-service is allowed to write this data until catalog-service
   exists.
3. This task must not read external service databases directly.
4. This is local import, validation, and documentation work inside
   recommendation-service.
5. Admin Page is not involved.
6. No Kakao response data is stored.
7. Recommendation reproducibility is affected through catalog/vector source
   hashes, so source hashes and validation reports must be deterministic.
8. RAG boundaries are unaffected.

## 5. Proposed Change

Add a catalog precision layer before changing the recommendation algorithm.

Implementation readiness gate:

```text
service boundary | database contract | recommendation contract |
verification contract
```

The smallest useful implementation:

- Add a beverage catalog audit service that validates:
  - every active beverage has one active `flavor_profiles` row
  - every active beverage has a `taste_v1` `recommendation_vectors` row
  - vector length exactly matches `taste_v1`
  - `vector_json` has all required dimension names and no unknown names
  - `confidence_json` includes every dimension or an explicit default policy
  - metadata includes `catalog_key`, `style`, `tags`, `source_type`,
    `source_version`, `curation_status`, and `reason_code_hints`
  - source metadata includes enough evidence to explain vector provenance
  - duplicate display names, duplicate catalog keys, and category/style gaps are
    reported
- Add a CLI:

```text
python -m app.tools.beverage_catalog_audit
```

- Add a machine-readable report format:

```text
reports/beverage_catalog_audit.json
```

- Expand tests so the current seed set is not only importable but also
  recommendation-quality complete.
- Keep existing tables if possible. Use `metadata_json` and `profile_json`
  before adding schema.
- If a database-level natural key becomes necessary, use an additive migration
  for `beverage_items.catalog_key` after updating `docs/database/erd.md`.

Quality gates:

```text
critical: import must fail or audit exits non-zero
warning: audit reports issue but import may still pass
info: report-only catalog coverage metric
```

Initial critical checks:

- missing active vector
- invalid vector dimension count
- unknown `taste_v1` dimension name
- missing catalog key
- duplicate catalog key
- missing curation status
- missing source version

Initial warning checks:

- low confidence across many dimensions
- missing Korean or English display name
- missing style
- missing tags or aliases
- weak reason-code coverage
- category under-representation

## 6. Database Plan

No schema migration is required for the first implementation.

Existing tables:

- `beverage_items`
- `flavor_profiles`
- `recommendation_vectors`
- `vector_schema_versions`
- `recommendation_staging.*`

Rollback:

```text
Disable or remove the audit CLI/tests. Existing beverage catalog rows remain
unchanged unless a later implementation explicitly updates seed metadata.
```

Optional future additive migration:

```text
beverage_items.catalog_key text unique
```

Only add this after proving `metadata_json.catalog_key` is insufficient.

## 7. API Plan

No public API or protobuf change is planned.

Internal/local command:

```text
Endpoint/RPC: none
Caller: operator/developer/CI
Auth: local runtime only
Request: optional data/report path
Response: console summary and JSON report
Errors: non-zero exit for critical catalog failures
Idempotency: report generation is deterministic for the same database contents
Audit: report contains generated_at, seed version, counts, and issue list
```

## 8. Migration Plan

No migration is planned for the first slice.

Production risk:

```text
Low. The first implementation is validation/reporting plus seed metadata
hardening. It should not alter serving behavior unless critical validation is
wired into import or CI.
```

## 9. Verification Plan

```text
- Unit: catalog audit detects missing vector, bad vector length, missing
  metadata, duplicate catalog key, and unknown dimensions.
- Unit: current seed records pass critical audit checks.
- Integration: beverage import remains idempotent.
- Docs: beverage catalog contract stays aligned with audit checks.
- Boundary: no survey-service or map-service database access.
- General: ruff, pytest, compileall, git diff --check.
```

## 10. Acceptance Criteria

The task is complete when:

```text
- [x] Beverage catalog audit service exists.
- [x] Audit CLI produces a JSON report with deterministic metrics and issue
      ordering.
- [x] Active seed beverages pass all critical quality checks.
- [x] Audit tests cover critical failure cases.
- [x] Catalog quality metrics include category, style, vector, confidence,
      source, and reason-code coverage.
- [x] No map-service or survey-service dependency is introduced.
- [x] No public API change is required.
- [x] Relevant tests and boundary checks pass.
```

## 11. Risks

```text
- Risk: catalog quality checks become too strict and block useful iteration.
  Mitigation: separate critical failures from warnings and info metrics.

- Risk: metadata remains too loose in JSON for long-term operations.
  Mitigation: start with audit reports; add schema only when a repeated query or
  uniqueness requirement is proven.

- Risk: AI-generated catalog enrichment introduces false flavor claims.
  Mitigation: require source/confidence metadata and operator-reviewed
  curation_status before active use.

- Risk: improving catalog data changes recommendation outputs.
  Mitigation: keep deterministic source hashes and add evaluation in plan 008.
```
