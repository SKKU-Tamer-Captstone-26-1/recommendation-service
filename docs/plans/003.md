# Selected Beverage Venue Recommendation Slice

## 1. Goal

Implement the first production-safe venue recommendation slice for a selected
beverage.

The slice must:

- consume map/place venue, menu, inventory, and price data only as read-model
  snapshots
- rank venues for an authenticated user who selected a canonical
  `beverage_items` record
- return differentiated purchase/drink options instead of near-duplicate venues
- apply freshness, confidence, distance, and budget rules deterministically
- persist recommendation request, result, explanation, and snapshot revision
  metadata for later audit
- keep PostgreSQL canonical for recommendation-owned state and treat Qdrant as
  optional/rebuildable only

## 2. Non-Goals

- Do not create or mutate canonical place, menu, inventory, or price data.
- Do not read the map-service/place-service database directly.
- Do not implement map-service admin APIs or owner workflows.
- Do not use Kakao Local/Map API as a bulk ingestion or canonical data source.
- Do not implement route optimization beyond MVP distance approximation.
- Do not require Qdrant for venue ranking in this slice.
- Do not implement assistant/RAG runtime.
- Do not support venue recommendations without a selected beverage yet.

## 5. Proposed Change

Implementation readiness gates:

```text
service boundary | API contract | database contract | sync contract |
recommendation contract | verification contract
```

The implementation adds `GetVenueRecommendations` for the authenticated user.
The request requires a selected active `beverage_id` and a user location. The
service loads eligible venue/menu/inventory/price snapshots from PostgreSQL,
applies hard filters, computes deterministic scores, returns differentiated
option types, and writes request/result/explanation logs with source revisions.

Initial option types:

```text
nearest_reasonable
best_price
balanced_best
```

The response should not return multiple venues that differ only by tiny score
changes. Each option type must have a clear selection rule and reason codes.

## 6. Database Plan

Existing read-model tables:

- `venue_snapshots`
- `venue_menu_snapshots`
- `venue_inventory_snapshots`
- `venue_price_snapshots`

Additive migration:

```text
Tables:
- map_snapshot_sync_cursors
- map_snapshot_sync_events

Columns:
- recommendation_results.source_snapshot_json jsonb not null default '{}'

Indexes:
- uq_map_snapshot_sync_events_event_id
- ix_map_snapshot_sync_events_status_retry(status, next_retry_at)
- ix_map_snapshot_sync_events_place(place_id)
- uq_venue_snapshots_place_revision(place_id, place_revision)
- uq_venue_menu_snapshots_identity(place_id, menu_item_id, menu_revision)
- uq_venue_inventory_snapshots_identity(place_id, beverage_item_id, source_beverage_id, inventory_revision)
- uq_venue_price_snapshots_identity(place_id, beverage_item_id, menu_item_id, price_revision)

Nullable identity columns must use `COALESCE` expression indexes or a normalized
identity key so PostgreSQL null semantics do not bypass idempotency.

Constraints:
- sync event status values are validated in service code for MVP
- no foreign key to map-service/place-service tables

Audit:
- sync events preserve source event payload, attempts, last_error, processed_at,
  and retry metadata
- recommendation result source snapshots preserve place, menu, inventory, and
  price revisions used for ranking

Lifecycle:
- snapshots are rebuildable derived state
- hidden, closed, duplicate_merged, archived, unpublished, expired, or
  insufficient-confidence snapshots are filtered, not mutated

Rollback:
- drop added sync tables and indexes
- drop `recommendation_results.source_snapshot_json`
- disable the venue RPC in service registration if rollback is needed
```

Table purposes:

| Table | Purpose | Canonical owner |
|---|---|---|
| `map_snapshot_sync_cursors` | Track map snapshot/event cursor progress | recommendation-service sync state |
| `map_snapshot_sync_events` | Idempotent processing and retry/dead-letter state for map events | recommendation-service sync state |
| `venue_*_snapshots` | Derived read model for ranking | map-service/place-service canonical source |

## 7. API Plan

Public RPC:

```proto
rpc GetVenueRecommendations(GetVenueRecommendationsRequest)
    returns (GetVenueRecommendationsResponse);
```

Caller:

```text
Client -> gateway-service -> recommendation-service
assistant-service -> recommendation-service for deterministic venue facts
```

Auth:

```text
JWT/gateway metadata only. Request must not include user_id or external_user_id.
```

Request shape:

```proto
message GetVenueRecommendationsRequest {
  string selected_beverage_id = 1;
  double lat = 2;
  double lng = 3;
  int32 radius_m = 4;
  int32 limit = 5;
  BudgetMode budget_mode = 6;
}
```

Response shape:

```proto
message VenueRecommendation {
  int32 rank = 1;
  string result_id = 2;
  string place_id = 3;
  string name = 4;
  string place_type = 5;
  string address = 6;
  VenueOptionType option_type = 7;
  double distance_m = 8;
  optional int32 price_krw = 9;
  VenueAvailabilityStatus availability_status = 10;
  VenueFreshnessStatus freshness_status = 11;
  double score = 12;
  repeated string reason_codes = 13;
  string explanation = 14;
  google.protobuf.Struct metadata = 15;
}
```

Metadata must include:

```json
{
  "place_revision": "place_rev_12",
  "menu_revision": "menu_rev_7",
  "inventory_revision": "inv_rev_8",
  "price_revision": "price_rev_3",
  "snapshot_synced_at": "2026-05-23T00:00:00Z",
  "inventory_confidence": 0.9,
  "price_confidence": 0.8,
  "distance_strategy": "straight_line_mvp"
}
```

Errors:

| Case | gRPC status |
|---|---|
| missing/invalid auth metadata | `UNAUTHENTICATED` |
| selected beverage does not exist or is inactive | `INVALID_ARGUMENT` |
| invalid lat/lng or radius | `INVALID_ARGUMENT` |
| profile missing/pending/failed | typed profile status with empty results |
| strict budget without valid price snapshot | omit venue or return `FAILED_PRECONDITION` if no valid candidates remain |

Idempotency:

- Recommendation reads are logged once per request.
- Interaction idempotency continues through `RecordRecommendationEvent`.
- Snapshot sync uses map event ID or snapshot export run ID as the idempotency key.

Audit:

- Every venue result must persist source snapshot revisions in
  `recommendation_results.source_snapshot_json`.
- Explanations must be deterministic templates from reason codes.

## 8. Sync / Import Plan

Supported inputs:

```text
1. map-service/place-service snapshot API or event stream when contract exists
2. signed/exported map snapshot fixture for local and pre-contract testing
```

Do not use:

```text
- direct map-service database reads
- Kakao bulk lookup
- scraped Kakao Local API responses
```

Processing rules:

- Upsert snapshots idempotently by source revision identity.
- Store source event payload and processing status before mutating read-model
  rows.
- Never reactivate or edit canonical place lifecycle state.
- If a source event says a place is hidden, closed, merged, or unpublished, mark
  the snapshot as ineligible for ranking.
- Dead-letter malformed events after configured retry attempts.

## 9. Recommendation Plan

Hard filters:

- selected beverage must be active in `beverage_items`
- venue status must be active and publication status must be published
- candidate must have menu or inventory evidence for selected beverage
- inventory must not be expired by more than the default exclusion window
- strict budget mode requires valid, non-expired price evidence
- distance must be within the requested radius

Freshness policy:

| Data | Fresh | Stale | Exclude By Default |
|---|---:|---:|---:|
| inventory | `<= 3 days` | `> 7 days` | `>= 30 days` |
| price | `valid_until` not expired | unknown or recently expired | expired by `> 30 days` |
| place | latest eligible snapshot | stale snapshot | hidden, closed, merged, unpublished |

Scoring components use active `scoring_v1` venue config:

```text
final_score =
  distance_fit
  + budget_fit
  + availability_confidence
  + price_confidence
  + freshness_adjustment
  + selected_beverage_match
```

Reason codes:

```text
NEARBY_VENUE
WITHIN_BUDGET
BEST_PRICE
LIKELY_AVAILABLE
FRESH_INVENTORY
BALANCED_BEST
SELECTED_BEVERAGE_AVAILABLE
```

Option selection:

| Option | Selection rule |
|---|---|
| `nearest_reasonable` | closest eligible venue above minimum availability confidence |
| `best_price` | lowest valid price, tie-broken by distance and confidence |
| `balanced_best` | highest final weighted score |

If two option types select the same venue, return it once with combined reason
codes and fill the next rank from the next best distinct venue.

## 10. Migration Plan

Type:

```text
additive schema migration
```

Backward compatibility:

- Existing beverage recommendation behavior continues unchanged.
- Existing recommendation results receive `{}` for `source_snapshot_json`.
- The venue RPC can remain unregistered until migration and tests pass.

Rollback:

- Disable the venue RPC.
- Drop additive sync tables and uniqueness indexes.
- Drop `source_snapshot_json` if no production venue result rows depend on it.

Production risk:

- Medium, because snapshot freshness and price confidence affect user-facing
  venue recommendations.
- Mitigate by serving only venues with explicit eligible snapshot evidence and
  logging all source revisions.

## 13. Risks

- Risk: map-service/place-service event contract is not finalized.
  Mitigation: start with a typed snapshot DTO and fixture importer; do not infer
  private schemas.
- Risk: stale inventory or price data could mislead users.
  Mitigation: exclude expired data by default and expose freshness/confidence in
  metadata.
- Risk: straight-line distance can be wrong for real travel.
  Mitigation: label the MVP strategy in metadata and defer route optimization to
  a later approved slice.
- Risk: venue scoring may appear precise despite weak source confidence.
  Mitigation: confidence directly affects score and reason codes.
- Risk: snapshot uniqueness indexes may fail if existing local data is dirty.
  Mitigation: migration should detect duplicates before adding constraints and
  document cleanup if needed.
