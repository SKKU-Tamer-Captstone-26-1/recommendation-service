# Interaction-Aware Beverage Suppression

## 1. Goal

Improve beverage recommendation quality by making the deterministic ranker
respect explicit negative user feedback before a learned model is available.

The immediate production behavior is:

```text
if a user recently dismissed a beverage recommendation,
do not recommend that same beverage again by default
```

This is not ML training. It is a safe feedback rule using
recommendation-owned interaction logs.

## 2. Non-Goals

- Do not train a model.
- Do not add collaborative filtering.
- Do not add a new database table.
- Do not change protobuf request/response shape.
- Do not read auth, survey, map, chatbot, or Flutter storage.
- Do not use chatbot messages as labels.
- Do not treat impressions alone as negative feedback.
- Do not suppress all similar styles yet.

## 4. Ownership Analysis

| Data | Owner | This task writes? | This task reads? | Allowed? |
|---|---|---:|---:|---|
| Recommendation requests/results | recommendation-service | yes | yes | yes |
| Recommendation interactions | recommendation-service | no new writes | yes | yes |
| Raw user identity | auth-service | no | auth-derived external user id only | yes |
| Chatbot conversation state | chatbot-service | no | no | yes |
| Survey answers | survey-service | no | no | yes |

Boundary decision:

```text
deterministic feedback suppression from recommendation-owned interaction rows
```

## 5. Proposed Change

When serving `GetBeverageRecommendations`, load recent beverage interaction
signals for the authenticated user:

```text
dismiss = negative explicit feedback
save/click/detail_view = positive or interest feedback
impression = exposure only
```

The latest signal per beverage wins:

```text
latest dismiss -> suppress beverage
latest save/click/detail_view -> do not suppress beverage
impression only -> neutral
```

Suppressed beverages are combined with explicit request exclusions:

```text
exclude_beverage_ids
exclude_result_ids
recent_feedback_suppressed_ids
```

## 6. Logging Plan

Persist suppression controls in `RecommendationRequest`:

```json
{
  "feedback_suppression": {
    "policy": "recent_dismiss_v1",
    "suppressed_beverage_ids": ["..."],
    "positive_beverage_ids": ["..."]
  }
}
```

Persist count-level request context:

```json
{
  "feedback_policy": "recent_dismiss_v1",
  "feedback_suppressed_count": 1,
  "feedback_positive_count": 2
}
```

Result source metadata should include the count only, not a large feedback log.

## 7. API Plan

No protobuf change.

The behavior is part of server-side personalization. Clients can still use
explicit `exclude_*` fields for chatbot follow-up turns.

## 8. Verification Plan

- Unit:
  - recent dismiss suppresses a high-scoring beverage
  - latest positive event prevents suppression
  - suppression is logged in request filters/context
- Regression:
  - explicit exclusions still work
  - diversity modes still work
  - record interaction validation still passes

## 9. Acceptance Criteria

```text
- [x] Beverage recommendations use recent dismiss feedback as a deterministic
      suppression signal.
- [x] Latest positive event can override older dismiss feedback for the same
      beverage.
- [x] Feedback controls are logged in request filters/context.
- [x] No schema migration or cross-service database read is added.
- [x] Tests and release gate pass.
```

## 10. Risks

```text
- Risk: accidental dismissal hides a beverage the user still wants.
  Mitigation: latest save/click/detail_view can make it eligible again; explicit
  client follow-up controls can still request alternatives.

- Risk: sparse feedback produces overfitting.
  Mitigation: only exact beverage IDs are suppressed; styles/categories are not
  suppressed in this slice.

- Risk: old feedback suppresses too long.
  Mitigation: policy is versioned as recent_dismiss_v1 and can later add TTL or
  user controls without schema changes.
```
