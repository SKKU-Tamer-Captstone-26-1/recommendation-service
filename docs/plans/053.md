# Plan 053 - Venue Place Type Request Filter

## Goal

Add a production-oriented request contract so venue recommendations can be
scoped to store, bar/pub, or outdoor-style place intents before map-service is
fully deployed.

## Problem

The venue recommendation API already accepts selected beverage, user latitude,
longitude, radius, limit, and budget mode. However, the original objective
requires future recommendations across bars, stores, and outdoor spots. Without
a request-level place type filter, Flutter, app-gateway-service, or
chatbot-service would need to filter locally or infer unsupported behavior.

That would weaken the recommendation boundary because clients could accidentally
rerank, hide, or reinterpret venue candidates outside recommendation-service.

## Scope

- Add `GetVenueRecommendationsRequest.place_types`.
- Keep `place_type` as map/place read-model metadata, not recommendation-owned
  canonical taxonomy.
- Resolve friendly request aliases such as `store`, `bar`, and `outdoor` to
  known snapshot `place_type` values.
- Filter venue snapshot candidates before ranking.
- Preserve the original snapshot `place_type` in response items.
- Log requested and resolved filters in `recommendation_requests`.
- Update Flutter, app-gateway, API, recommendation logic, and read-model docs.
- Add focused tests for alias filtering and invalid filters.

## Non-Goals

- No map-service canonical schema change.
- No map-service implementation.
- No direct map/place storage read or write.
- No migration.
- No route optimization change.
- No venue scoring formula change.
- No Flutter, gateway, chatbot, or LLM implementation.

## Boundary Decision

Canonical place/menu/inventory/price data remains owned by map-service or
place-service. recommendation-service only consumes published read-model
snapshots and uses `place_type` as a request constraint for deterministic
ranking.

## Acceptance Criteria

- [x] Proto request includes repeated `place_types`.
- [x] gRPC handler forwards `place_types` to the service layer.
- [x] Service filters venue candidates by normalized place type aliases before
  ranking.
- [x] Unknown place type filters fail as invalid requests.
- [x] Recommendation request logs include requested and resolved filters.
- [x] Response items preserve original snapshot `place_type`.
- [x] Docs describe Flutter/gateway behavior and service boundary.
- [x] Focused tests pass.
- [x] Release gate passes.

## Rollback

Rollback is additive-contract safe while no client depends on the field. Remove
`place_types` from the proto/generated binding, remove service filtering, remove
tests, and revert docs to the previous unfiltered venue contract.
