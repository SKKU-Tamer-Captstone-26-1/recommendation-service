# Beverage Follow-up Diversity Contract

## 1. Goal

Make beverage-focused chatbot follow-up requests deterministic and
production-safe by letting `recommendation-service` handle exclusion and
diversity controls for beverage recommendations.

The immediate user-visible goal is:

```text
"다른 술 추천해줘" should not depend on chatbot-side arbitrary filtering.
chatbot-service should call recommendation-service with explicit exclusions and
diversity intent, and recommendation-service should return a reproducible
ranked list.
```

## 2. Non-Goals

- Do not implement venue/place recommendation improvements in this plan.
- Do not implement chatbot intent routing or LLM prompt changes here.
- Do not call the LLM from recommendation-service.
- Do not add RAG.
- Do not read chatbot, survey, auth, map, or gateway databases.
- Do not make random ranking changes.
- Do not change beverage catalog ownership.


## 5. Proposed Change

Add fields to `GetBeverageRecommendationsRequest`:

```text
exclude_beverage_ids
exclude_result_ids
diversity_mode
```

Add enum:

```text
BeverageDiversityMode
```

Supported initial modes:

```text
BEVERAGE_DIVERSITY_MODE_STANDARD
BEVERAGE_DIVERSITY_MODE_DIFFERENT
BEVERAGE_DIVERSITY_MODE_ADJACENT
```

Implementation readiness gates:

```text
API contract
recommendation contract
verification contract
```

## 6. Database Plan

No schema migration.

Existing request/result logs already store:

```text
filters_json
request_context_json
ranked RecommendationResult rows
```

The new request controls will be stored in `filters_json` and
`request_context_json`.

Rollback:

```text
Ignore the new request fields and redeploy the previous service revision.
```

## 7. API Plan

Endpoint/RPC:

```text
RecommendationService.GetBeverageRecommendations
```

Caller:

```text
chatbot-service, app-gateway-service, Flutter through app-gateway
```

Auth:

```text
authorization: Bearer <auth-service-jwt>
x-serverless-authorization when called through private Cloud Run
```

Request:

```text
category
limit
budget_mode
exclude_beverage_ids
exclude_result_ids
diversity_mode
```

Response:

```text
Same response shape. Ranking remains recommendation-service owned.
```

Errors:

- invalid UUID in `exclude_beverage_ids`
- invalid UUID in `exclude_result_ids`
- unsupported `diversity_mode`
- strict budget remains unavailable until approved price semantics exist

Idempotency:

```text
Read RPC only. Recommendation request logs are written for observability, as
current behavior already does.
```

Audit:

```text
Store exclusions and diversity mode in recommendation request filters.
```

## 8. Migration Plan

No migration.

## 9. Verification Plan

- Unit:
  - excluded beverage IDs are not returned
  - excluded result IDs resolve to target beverage IDs and are not returned
  - different mode avoids returning the same dominant style when possible
  - adjacent mode can return adjacent non-identical categories/styles while
    preserving deterministic order
- API:
  - proto request accepts new fields
  - gRPC service passes fields to the recommendation service
- Docs:
  - API contract documents chatbot follow-up usage
  - recommendation logic documents deterministic diversity controls

## 10. Acceptance Criteria

The task is complete when:

```text
- [x] New request fields are additive and do not break existing callers.
- [x] Chatbot can request "different beverage" without client-side reranking.
- [x] Recommendation-service logs exclusion/diversity controls.
- [x] Focused tests pass.
- [x] No venue/map/LLM/chatbot logic is implemented here.
```

## 11. Risks

```text
- Risk: small catalog can return fewer results after exclusions.
  Mitigation: return fewer results rather than fabricating candidates.

- Risk: "different" is interpreted too strongly.
  Mitigation: mode is deterministic and bounded; it avoids exact excluded
  beverages first, then uses style/category spacing when possible.

- Risk: generated proto bindings drift.
  Mitigation: update proto and generated Python binding together in this repo.
```
