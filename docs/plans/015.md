# Versioned Beverage Budget-Aware Scoring

## 1. Goal

Improve beverage recommendation quality by replacing the placeholder beverage
`budget_fit = 0.5` feature with a deterministic, source-aware soft budget
feature based on human-reviewed catalog KRW price ranges.

The immediate production goal is:

```text
drink ranking should consider the user's survey budget when safe catalog price
evidence exists, without pretending catalog prices are live store offers.
```

## 2. Non-Goals

- Do not use venue/menu live price snapshots for beverage-only ranking.
- Do not enable strict beverage budget filtering.
- Do not call map-service, survey-service, auth-service, chatbot-service, or
  any external price source.
- Do not read another service's database.
- Do not train an ML model.
- Do not mutate `scoring_v1` behavior silently.
- Do not change the public protobuf request/response shape.

## 5. Proposed Change

Add `scoring_v2` as a versioned config instead of changing `scoring_v1` in
place.

`scoring_v2` keeps the same high-level weights as `scoring_v1`, but documents
these feature strategies:

```text
beverage budget feature = catalog_price_range_soft_v1
venue distance feature = route_ready_distance_feature_v1
```

Runtime services should use `Settings.active_scoring_config` instead of
hardcoding `scoring_v1`.

Default runtime target after this plan:

```text
ACTIVE_SCORING_CONFIG=scoring_v2
```

Rollback:

```text
ACTIVE_SCORING_CONFIG=scoring_v1
```

## 6. Budget Feature Contract

Input:

```text
profile.budget_range
beverage.price_min_krw
beverage.price_max_krw
beverage.metadata_json.price_policy
beverage.metadata_json.price_observation_summary
```

Output:

```json
{
  "strategy": "catalog_price_range_soft_v1",
  "fit": 0.86,
  "confidence": 0.65,
  "budget_range": "30000_100000",
  "budget_floor_krw": 30000,
  "budget_ceiling_krw": 100000,
  "price_min_krw": 39000,
  "price_max_krw": 45000,
  "price_mid_krw": 42000,
  "price_policy": "verified_krw_observations_not_live_truth"
}
```

Rules:

- Missing budget or missing price evidence returns neutral fit.
- Broad catalog price range is a soft ranking signal only.
- `over_200000` means premium-tolerant, not a hard ceiling.
- Prices above a user's upper budget reduce fit gradually.
- Cheaper-than-range items are not rejected.
- The feature confidence pulls weak price evidence toward neutral.

## 9. Verification Plan

- Unit:
  - budget-aware beverage fit rewards in-budget catalog price ranges
  - missing price evidence stays neutral
  - expensive beverages are penalized for low-budget users
  - `scoring_v2` active config can be selected by settings
- Migration:
  - migration is additive and rollback deprecates `scoring_v2`
- Regression:
  - existing beverage/venue recommendation tests pass
  - release gate passes

## 10. Acceptance Criteria

```text
- [x] `scoring_v2` exists as a versioned config.
- [x] Runtime recommendation/profile generation can use configured scoring
      version instead of hardcoded `scoring_v1`.
- [x] Beverage scoring uses catalog price ranges as soft budget evidence.
- [x] Budget feature metadata is logged with recommendation model features.
- [x] `scoring_v1` remains available for rollback.
- [x] No live venue price, map-service DB, or external price lookup is used.
```

## 11. Risks

```text
- Risk: catalog price ranges are stale or broad.
  Mitigation: low feature confidence and explicit policy metadata.

- Risk: users interpret catalog price as live store price.
  Mitigation: response metadata preserves price policy; strict budget remains
  unavailable for beverage-only recommendations.

- Risk: changing active scoring changes ranking.
  Mitigation: use `scoring_v2`, keep `scoring_v1`, and allow env rollback.
```
