# Plan 043 - Taste-Direction Follow-up Evaluation Gate

## Goal

Add deterministic release evidence for beverage follow-up requests that change a
flavor direction, such as "sweeter", "less smoky", "lighter/crisper", or
"more herbal/bitter".

## Problem

The service already supports deterministic `DIFFERENT` and `ADJACENT` diversity
follow-ups, but that only prevents repeated recommendations. It does not prove
the scoring stack is ready for chatbot requests like "더 달게 추천해줘" or "덜
피트하게 추천해줘".

Adding a live `flavor_direction` API field immediately would require proto,
gateway, chatbot, request logging, and Flutter contract work. Before doing that,
the recommendation service needs offline evidence that the catalog, survey
mapper, and beverage scoring function respond correctly to direction changes.

## Scope

- Add optional `directional_followups` to drink evaluation fixtures.
- Derive synthetic profile variants from fixture-level survey answer overrides.
- Reuse the normal `score_beverage_candidate` function for every directional
  follow-up case.
- Require fixture-approved positive candidates to score above explicit negative
  counterexamples.
- Add aggregate metrics and failure payloads to the drink evaluation report.
- Add CLI thresholds and release-gate thresholds.
- Add focused success and intentional failure tests.
- Document the release-gate contract and future API boundary.

## Non-Goals

- No live `flavor_direction` proto field.
- No chatbot-service change.
- No Flutter change.
- No scoring formula change.
- No DB schema or migration change.
- No LLM or RAG ranking behavior.

## Acceptance Criteria

- [x] Evaluation fixtures include at least 6 directional follow-up cases.
- [x] Directional follow-up fixtures cover at least 6 distinct directions.
- [x] Current reviewed seed catalog keeps
  `directional_followup_score_preference_rate = 1.0`.
- [x] Directional follow-up failure payloads include fixture, direction,
  positive keys, negative keys, scores, missing keys, and top results.
- [x] The evaluation CLI exposes directional follow-up thresholds.
- [x] The release gate requires all declared directional follow-ups to pass.
- [x] Focused tests cover success and intentional failure cases.

## Rollback

Remove `directional_followups` from the fixture file, remove the directional
metrics and CLI thresholds, and remove the release-gate threshold only if product
review accepts launching flavor-direction chatbot requests without offline
recommendation-service evidence.
